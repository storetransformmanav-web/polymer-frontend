# CLAUDE.md

Guidance for AI coding agents working in this repository. Read this before adding or moving files.

## What this app is

Polymer CRM surfaces a client's Shopify orders and products (and eventually inventory) in one place. **Shopify sync is a backend concern** — this frontend must never call Shopify's Admin API directly (that needs credentials that don't belong in a browser). It calls our own backend through `src/lib/api/client.ts` (Axios), which syncs with Shopify. Products, Customers and Orders read the real backend; no feature runs on mock data any more — the "Mock data" pattern below is kept as a recipe for a new feature that has no backend yet.

## Stack (do not change without a strong reason)

- **React 19, Vite 8, TypeScript** (`strict: true`) — every source file is `.ts`/`.tsx`. Don't add a new `.js`/`.jsx` file.
- Package manager: **npm** (`package-lock.json` is committed — don't switch to yarn/pnpm).
- **Styling: Tailwind CSS v4** (`@tailwindcss/vite`), utility classes directly in JSX. **No per-component `.css` files and no hand-written CSS** — the only CSS file in the project is `src/styles/globals.css` (the `@import 'tailwindcss'`, the `@theme` token block, and the dark-mode variable overrides). See "Styling" below.
- Linting: **Oxlint** (`.oxlintrc.json`, with the `typescript` plugin enabled) — not ESLint.
- Formatting: **Prettier** (`.prettierrc.json`, with `prettier-plugin-tailwindcss` — it sorts class lists on format, don't hand-order them).
- Routing: **react-router-dom** (`createBrowserRouter`).
- **Server state: TanStack Query** (`@tanstack/react-query`) — every feature's `hooks/use*.ts` that fetches data wraps `useQuery`/`useMutation`, not a hand-rolled `useEffect`+`useState` fetch. The `QueryClient` lives in `src/app/queryClient.ts` and is provided in `AppProviders`.
- **Client/global state: Redux Toolkit** (`@reduxjs/toolkit` + `react-redux`) — the store is `src/app/store/store.ts`, with one slice per concern (currently just `ui`, for theme + sidebar-collapsed). Use the typed hooks in `src/app/store/hooks.ts` (`useAppDispatch`/`useAppSelector`), never the plain `react-redux` ones.
- **HTTP: Axios**, wrapped by `src/lib/api/client.ts` (`apiClient`). Never call `axios`/`fetch` directly from a feature.
- **Runtime validation: Zod** — a feature that fetches data defines a schema in `features/<name>/schemas/`, derives its TS types from that schema (`z.infer`), and validates network responses against it at the API boundary. See "Mock data" below.
- **Image lightbox: `yet-another-react-lightbox`** — the only viewer for product images (Overview gallery and Media tab, `features/products/components/ProductLightbox.tsx`). It is loaded on demand (`React.lazy`), so it and its stylesheets only download when an image is opened. Importing its three library `.css` files (in `ProductLightboxView.tsx`) is the one exception to "`globals.css` is the only CSS" — they are third-party styles, not ours. Image URLs still go through `safeUrl` (`utils/slides.ts`) and the lightbox sets `referrerPolicy: 'no-referrer'`. Don't add a second lightbox/carousel library.
- **Rich-text editor: TipTap** (`@tiptap/react` + `starter-kit` and the text-style/colour, text-align, image, table and YouTube extensions) — the only editor for HTML content, used for a product's description (`components/ui/RichTextEditor.tsx`). It is loaded on demand (`React.lazy`, chunk entry in `richTextEditorChunk.ts`; `preloadRichTextEditor` runs when the pointer reaches the Description pencil, so it is normally there by the click), so it only downloads when an editor is shown. Don't add a second editor library. Its schema is what keeps HTML safe (see "Safe rendering").
- Testing: **Vitest** + **React Testing Library**, jsdom environment.

## Architecture: feature-based

```

├── main.tsx               # entry point only — no logic here
├── vite-env.d.ts            # Vite client types + ImportMetaEnv typing
├── app/                     # composition root, not a feature
│   ├── App.tsx              # AppProviders > AppRouter, nothing else
│   ├── providers/            # AppProviders.tsx — Redux + React Query providers
│   ├── store/                 # Redux: store.ts, uiSlice.ts, hooks.ts (typed dispatch/selector)
│   ├── queryClient.ts           # the app's single QueryClient
│   ├── router/                   # route table (AppRouter.tsx) + navigation.ts + NotFoundPage
│   └── layouts/                    # shared page chrome, rendered via <Outlet/>
├── features/<name>/          # one directory per business domain
│   ├── components/            # feature-only components
│   ├── hooks/                  # feature-only hooks — use*.ts wrapping useQuery/useMutation
│   ├── api/                     # this feature's requests, built on lib/api/client.ts
│   ├── schemas/                  # Zod schemas — the source of truth for this feature's types
│   ├── pages/                     # route-level components
│   ├── utils/                      # feature-local helpers
│   └── index.ts                     # PUBLIC EXPORTS — the only import surface
├── components/ui/            # generic reusable primitives (Button, Logo, StatCard,
│                              # PageHeader, Table, Badge, ThemeToggle, icons.tsx, ...)
├── hooks/                     # generic shared hooks (used by 2+ features)
├── lib/api/                    # apiClient (Axios wrapper) + ApiError
├── lib/format.ts                 # shared Intl currency/date formatters
├── config/env.ts                   # the only place import.meta.env is read
├── assets/                          # static files (logo, ...) imported by components
├── styles/globals.css                # the ONLY .css file — @theme tokens + dark-mode overrides
└── test/                              # setup.ts (jest-dom) + renderWithProviders.tsx
```

`app/router/navigation.ts` is the single list of top-level routes (path, label, icon). `NAV_ENTRIES` is what the sidebar renders: plain links plus accordion groups — currently Dashboard, then **Shopify Management** (a `NavGroup` holding Orders, Products, Customers, Inventory and Lock Management; closed by default, opens on click, and starts open when the current page is one of its links; see `NavAccordion.tsx`). **In the icon rail (sidebar closed) a group is just its icon, and clicking it opens a card to the right of the rail** (`NavGroupFlyout.tsx`: the group's name in small capitals, then each page with its icon and label, the current page tinted; portalled and fixed to the screen, closes on Escape, an outside click, choosing a page, scroll or resize) — any group with several pages gets this automatically. `NAV_ITEMS` is the same routes flattened, which `AppBar` uses for the page-title heading. Add a route there, not in each component separately.

### Styling

**Text size is one scale for every page**: `html { font-size: 93.75% }` in `globals.css` (15px root, not 16px). Type and spacing are in `rem`, so this shrinks every page together — change that one number to resize the whole app; don't set a different size on a page.

Every component is styled with **Tailwind utility classes in `className`** — no `ComponentName.css` files, no `styled-components`, no CSS modules.

- The brand palette lives in `src/styles/globals.css` under `@theme` (`--color-accent`, `--color-text`, `--color-border`, ...). Because `@theme` declares real CSS custom properties, every Tailwind utility it generates (`bg-accent`, `text-text-muted`, `border-border`, `font-sans`, ...) compiles to `background-color: var(--color-accent)` etc — **not** a literal hex value.
- Dark mode is **not** done with Tailwind's `dark:` variant. It's done by re-declaring those same custom properties under `@media (prefers-color-scheme: dark)` and `:root[data-theme='dark']` in `globals.css` (see `src/app/store/uiSlice.ts` for how `[data-theme]` gets set). Since every color utility already resolves through `var(--color-*)`, this re-themes the whole app automatically — **don't add `dark:` variant classes anywhere**, they're redundant and will drift from the real mechanism.
- When a warning/danger/etc. tone needs a color Tailwind doesn't ship a semantic token for (e.g. a tinted background), add it to `@theme` in `globals.css` (see `--color-warning-bg`, `--color-danger-bg`) rather than hand-picking a Tailwind palette color that won't adapt for dark mode.
- For layout constants that matter exactly (sidebar width, header height), use Tailwind's arbitrary value syntax (`w-[232px]`) rather than the nearest scale step.
- A component's own file is `.tsx` only — if two or more class names always travel together, extract a local `const` (e.g. `FILTER_LABEL = '...'` in `OrdersPage.tsx`) rather than reaching for a CSS class.
- Run `npm run format` after editing className strings — `prettier-plugin-tailwindcss` sorts them into Tailwind's canonical order; don't hand-order them.

**Details-page cards** have a sage-green border by default (`DETAIL_CARD` in `DetailSection.tsx`: `border-border-strong`, `#b4c9b8`; dividers inside use it too). The hover colour is on the **title row only**, never the whole card: a `DetailSection`'s header row and each `DescriptionAccordion` row take `hover:bg-accent-tint/60` (the same tint as a hovered table row). Don't add a hover border to a whole card. (An order's details page differs: its cards' title rows, `TITLE_ROW` in `OrderCompact.tsx`, have that tint all the time.)

### Import extensions

`tsconfig.app.json`/`tsconfig.node.json` use `moduleResolution: "bundler"` with `allowImportingTsExtensions: true`. **Import with the real extension** (`'./Foo.tsx'`, `'./bar.ts'`), not a `.js` placeholder — that convention is for Node's `nodenext` resolution, which this project doesn't use.

## Where things go

- **New page/route** → `features/<name>/pages/`, then export it from `features/<name>/index.ts`, then add a route entry in `app/router/AppRouter.tsx` pointing at that export.
- **New feature** → create `features/<name>/` with only the subdirectories it needs (a simple feature might only need `pages/` and `index.ts` — don't scaffold empty `schemas/`/`utils/` folders in advance).
- **Data fetch** → define the shape in `features/<name>/schemas/` (Zod schema + `z.infer` type), add a function in `features/<name>/api/` that calls `apiClient` and validates the response against that schema, then a `hooks/use*.ts` that wraps it in `useQuery` (or `useMutation` for writes). Never call `apiClient`/Axios/`fetch` directly from a component. (A feature with no backend yet uses a `mock*.ts` in `api/` instead of a real backend call — see "Mock data" below for how to graduate it to real.)
- **New backend-facing error handling** → throw/catch `ApiError` (`src/lib/api/ApiError.ts`); check `.status`/`.data`, don't re-parse Axios errors in feature code.
- **Reusable UI with zero feature knowledge** (Button, Modal, Input, Card) → `components/ui/`. If it references a specific feature's data shape, it isn't generic — keep it in the feature.
- **Reusable hook with zero feature knowledge**, used by 2+ features → `hooks/`. Otherwise keep it inside the feature that uses it.
- **Env var** → add it to `.env.example`, declare it on `ImportMetaEnv` in `src/vite-env.d.ts`, and read it through `src/config/env.ts`. Never call `import.meta.env` from anywhere else.
- **Global client state** (something read/written from 2+ unrelated components, needs to persist, or both) → a new slice under `src/app/store/`, registered in `store.ts`'s `reducer` map. Expose it to the app through a small hook in `src/hooks/` (see `useTheme.ts`/`useSidebarCollapsed.ts`) rather than having components call `useAppSelector`/`useAppDispatch` directly everywhere — that hook is the seam if the underlying state mechanism ever changes.
- **Server state** (anything fetched from an API) → TanStack Query via a feature's `hooks/use*.ts`, not Redux. Redux is for client-owned state only.
- **New top-level route** → add it to `src/app/router/navigation.ts` (path, label, icon — inside the Shopify Management group's `items` if it's a Shopify page), then wire the route in `AppRouter.tsx`. Don't add nav links directly in `Navbar.tsx`.
- **Icon** → `src/components/ui/icons.tsx` has a small hand-written set (no icon library is installed). Add new ones there in the same stroke style rather than pulling in a dependency for one glyph. **Never use emoji as icons** — always an SVG from this file.

## Backend API (auth)

- **All real backend endpoints live in one file: `src/lib/api/endpoints.ts`** — path (`ENDPOINTS`), Zod response schema, and request function (`api.auth.requestOtp`, ...). Add new endpoints there. Its schemas live in that file (not in `features/*/schemas/`) so `lib/` never imports from a feature.
- **Auth is passwordless (email OTP) and runs on Redux Toolkit**: `src/app/store/authSlice.ts` holds the login-flow state (`step`, `email`, statuses, `error`) and the persisted `session`; `requestOtp`/`verifyOtp` are `createAsyncThunk`s that call `api.auth.*`. Components use `features/auth/hooks/useLogin.ts` (flow) and `hooks/useAuth.ts` (session/logout), never the slice directly. This is a deliberate exception to "server state → TanStack Query": a login flow is client-owned state, not a cached resource. The backend rate-limits code requests per account (429 "Please wait N seconds…"): that means a code was already sent and is still valid, so `requestOtp` resolves as `rateLimited` — the flow moves to the code screen with the backend's message and a resend timer of exactly N seconds (`resendAvailableAt`, parsed by `parseWaitSeconds`) instead of stranding the user on an error. A 429 without a readable wait time is still shown as an error.
- **Staying signed in**: the email step of the login page has a **"Remember me" checkbox** (unticked by default; `authSlice.rememberMe`, `rememberMeChanged`, `useLogin().rememberMe/setRememberMe`; it also applies to Google sign-in, whose button is on the same step, and survives "Use a different email"). **Ticked: the session lasts 30 days** — both sign-in calls (`POST /auth/otp/verify` and `POST /auth/google`) send `remember_me: true` and the backend issues a 30-day token (`expires_at`). **Unticked: the default session** — they send `remember_me: false` (the backend's own default, a 1-day token) and the app ends the session after 1 day (`DEFAULT_SESSION_DAYS`). `sessionExpiry(backendExpiresAt, now, rememberMe)` (authSlice) sets the session's `expiresAt` to the sooner of the backend token's expiry and now + 30 days (or + 1 day without it). **The idle limit is the backend's, not a number in the app**: `idle_timeout_minutes` (1440 — 24 hours — now, for every role) comes with `POST /auth/otp/verify`, `POST /auth/google` (both, the same way) and `GET /auth/csrf` (after every page reload), is kept in the session (`Session.idleTimeoutMinutes`, `readIdleTimeoutMinutes` / `DEFAULT_IDLE_TIMEOUT_MINUTES` in `lib/idleTimeout.ts`, 1440 when an answer does not say) and is what `useSessionGuard` waits for: that long with no activity signs you out, with or without "Remember me" ( pointer, keys, wheel and scroll count, background requests don't; the keep-alive ping's `GET /auth/csrf` answer updates the limit (`idleTimeoutUpdated`); the time is kept in localStorage under `SESSION_ACTIVITY_KEY`, so activity in one tab keeps the others in, and a browser reopened after the limit is signed out at once; a new sign-in restarts it): `logout('idle')`, which also revokes the token, and the login page says why. The backend should enforce its own limit too. When the session itself passes, `useSessionGuard` signs out with `logout('expired')`, which also revokes the token, and the login page says the session has expired (`SignOutReason` is `'expired' | 'idle'`). **The answer's `user.permissions`** (access by area: `{ products: { view, manage }, … }`) drives `hooks/useAccess.ts`: `view: false` leaves the page out of the sidebar (`visibleNavEntries`, by `NavItem.area`) and its address shows `NoAccessPage`; `manage: false` hides the Sync button and the customers Export. **The `office` role** (`user.role`, any letter case; `isOfficeRole` in `hooks/useAccess.ts`) sees only the Shopify Management group — the sidebar leaves out every other entry (`visibleNavEntries`' `role` argument, `SHOPIFY_PATHS` in `navigation.ts`) and `DashboardLayout` sends an office user from any other address (the dashboard after sign-in, a bookmark) to `/orders`. Only an explicit `false` hides anything (an area the answer doesn't name stays allowed), add/edit/delete buttons are not gated yet, and **none of this is the protection: the stored session can be edited, so the backend must refuse**. **The permission names are the backend's real ones** (each has `view` and `manage`): `orders`, `products`, `customers`, `inventory`, `access` (Lock Management — the name is `access`, not `locks`), `users`, `activity` (a page's `area` in `navigation.ts`), `customers_export` (the Customers CSV Export button: `view` and `manage` both needed), `sync` (the top-bar Sync buttons: `view` and `manage` both needed, whatever the page's own `manage` says), plus `sage_invoices`, `roles` and `shops`, which have no screen here yet. A hidden screen opened by hand still gets 403 from the server. A **429** on the customer lists or exports means the hourly limit was reached: the backend's message (it says when to try again) is shown as it is, never retried. A session removed in another tab (logout there) signs out here too.
- **Google sign-in** (`POST /auth/google`) sends the Google ID token; `features/auth/utils/googleIdentity.ts` loads Google's GIS script (no npm package) and `GoogleSignIn.tsx` renders Google's own button. **Every sign-in has its own nonce**: `createNonce()` (24 random bytes, base64url, 32 characters) is given to Google in `initialize({ nonce })` — so it is inside the ID token — and sent to the API as `nonce` next to the `credential`; a fresh one replaces it the moment a credential comes back (success or failure), so none is used twice. It needs `VITE_GOOGLE_CLIENT_ID`; when empty, production hides the Google option and development shows a disabled placeholder with setup instructions. The thunk is `googleSignIn` in `authSlice.ts`.
- **Products** (`GET /products`) is real-API and lives in Redux: `src/app/store/productsSlice.ts` holds the filters, a per-query page cache (stale-while-revalidate, 30s), the previous results shown while the next query loads, accumulated filter options, recently-opened products and the open product. `features/products/hooks/useProducts.ts` is the only consumer; The list loads when the page is opened (a click on its sidebar link) — **not at sign-in, not when the link is hovered, and no next page ahead of time**; a page is requested when its pagination button is clicked. This is a deliberate exception to "server state → TanStack Query" (Customers and Orders do the same). The cache is cleared on logout/expired session.
- **Product details** (`GET /products/{id}`, UUID or Shopify ID — not the handle) render in the _same page_ at `/products/:id` (route `products/*` → `ProductsPage`), never in a slide-over. Opening is only via the product name, the View button or the mobile card (not the rest of the row). **Open on the store**: there is no Shopify column — each row's external-link icon sits in the Product cell **right after the copy icon**, both in the same 20px box with a 15px icon so they line up (`ShopifyLink` in `ProductsList.tsx`). It opens the product's page on the public store in a new tab — `https://polymeruk.com/products/<handle>` (`storefrontProductUrl` in `utils/format.ts`: only the row's `handle` is taken from the data, as one URL-encoded path segment; a row with no handle draws **no icon**, never a guessed link). It is a real link with `rel="noopener noreferrer"` and does not open the product in the CRM. (The product page's SEO card also has "Open live page" → the Shopify admin address, `shopifyAdminProductUrl`.) The phone cards have no such link. **Copying a name**: in the desktop table a small copy icon (`components/ui/CopyButton.tsx`) is **always visible**, vertically centred right beside a product's name (name and icon are both 20px high); clicking it copies exactly the product name (it does not open the product) and shows a tick for a moment. Clicking a row's _image_ instead opens a right-hand quick-view panel (`ProductQuickView`, local state in `ProductsPage`) built from the already-loaded list row, with an "Open full details" button. In the Overview tab the left column shows the main image plus a single scrolling row (`components/ui/ScrollRow.tsx`, with arrows that appear only when there is more to scroll) of a thumbnail of every product image; clicking any of them (or "View Full", or an image on the Media tab) opens the lightbox. There is **no "Status & Launch" card** (removed by choice; a product's status is changed from the dropdown in the list's row); "Description" starts collapsed (`defaultOpen={false}`); "Product Specifications" starts open. **The lightbox shows each picture's information** in a card at the top right beside the picture (`ProductLightboxView`, `render.controls`: a frosted-glass "Information" card — an info icon and heading, then **Name** (the file name from its address, `fileNameOf`), **Alt text** (`alt_text`; "No alt text" in grey italics when it is empty), **Details** (type from `mime_type` — "JPG" — and "width × height px") and **ID** (the image's `id`, with a copy button); the API gives no file size, so none is shown. The card is placed 16px from the shown picture's right edge (`ImageInfoCard` measures `.yarl__slide_image` **on every animation frame** — a single measurement ran before the library had fitted the picture and left the card on top of it; top-right of the window when there is no room beside it); it follows the picture when paging; `LightboxSlide.altText` is unset — so no panel — for a slide that isn't a product image). The page keeps a strip of open-product **tabs** (`tabs` in `productsSlice`). Details are cached in the slice (`details`); hovering the name or View prefetches them, and the header draws from the already-loaded list row (`preview`) while the rest loads. The **Metafields tab is written for people, not for developers** (`MetafieldsPanel`, with the pure helpers in `utils/metafields.ts`, tested): a one-line explanation of what metafields are; then a table of Detail (a plain name — `unit_of_sale` → "Unit of sale", with its group and the technical `namespace.key` in small grey underneath), Applies to ("Whole product" or "Variant: …"), Kind (`number_integer` → "Whole number", `list.single_line_text_field` → "List of text (one line)"…) and Value laid out by its kind (numbers formatted, Yes/No, dates, lists as chips, small objects as label/value rows, money/weight/rating as words, colours with a swatch, links only if http(s), Shopify references as "Product 42"); structured data has a **"View details" button that opens its full value in a right-hand panel** (`MetafieldDetailsModal`, on the shared `components/ui/SidePanel.tsx`, laid out like the products list's picture quick view), **read out for people and never shown as JSON**: `readableMetafield` / `readableValue` / `readableSections` in `utils/metafields.ts` (tested) turn the value into names and values (keys become plain names — `accent_color` → "Accent color" —, true/false become Yes/No, **a colour — a hex code or an `rgb()` / `rgba()` / `hsl()` / `hsla()` value, and nothing else, so it is safe to paint — becomes a swatch beside its code (a see-through one over a chequerboard)**, a list of words becomes chips, anything larger a list of boxes, text with tags is drawn through `SafeHtml`, a rich-text value becomes its words), at most 100 list items and 6 levels deep; for the description-sections detail the panel shows only "Settings of the description app" by name (the sections' titles and text are not repeated — the Overview's accordion shows them). The panel slides in from the right like the quick view (`ProductQuickView`): a "Metafield details" header bar with ✕; the detail's plain name, "Applies to · Kind" and the technical `namespace.key` (with a copy button); names and values as the quick view's rows (name muted on the left, a short value on the right, a longer one under its name); lists of words as accent chips like its tags; and a full-width **Close details** button at the foot. It closes with that button, the ✕, Escape or a click on the backdrop. The `apd` description-sections metafield is described ("2 sections: …", shown in the Description card) instead of printing its JSON. Nothing is hidden: every metafield of the product and of each variant is listed. There is **no Raw data tab** on a product (removed): the product page never asks for the large Shopify `raw_json` (`include_raw` is always sent as `false`; the slice still knows how to cache a raw copy under `"id|raw"`, unused by the page). Product description HTML is never injected as markup (the Description card rebuilds it through `SafeHtml`; elsewhere it is plain text via `htmlToText`) and links go through `safeUrl` — see also the **description sections** below, which are rebuilt by a whitelist renderer, never injected as markup. **Description sections**: the details call is `GET /products/{id}?include_raw=false&shop=` (`api.products.details`; the answer is `{ product: {…} }`; `include_raw` is always sent because the API's own default is `true`, and the large raw payload is only asked for when the Raw data tab opens). Many stores keep their description as sections ("Product Description", "Product Information"…) saved by a description app in the product metafield **`apd` / `apd`** (a JSON string: `{ sections: [{ title, content (HTML), position }], accordian_multi, … }`). `readDescriptionSections` (`utils/descriptionSections.ts`, Zod-checked; a missing, damaged or title-less value gives nothing) reads them in `position` order, and the **Overview tab shows them on their own as an accordion — there is no "Description" card around them** (`DescriptionSectionsBlock` in `ProductDetailPanels.tsx`: a slim row with just the pencil — an `EditableTab` — above `DescriptionAccordion.tsx`, which sits right under the Product Specifications card: a bordered row per section with its title and a chevron, all closed to begin with; `accordian_multi: false` makes opening one close the others). The product's own `description_html` is shown **first, above the sections** (Shopify description, then Product Description, then Product Information) as a separate, closed **"Shopify description"** card (`EditableCard`, same rich-text pencil as the no-sections card — `Edit Shopify description`) (just its text — no explanatory note above it). Only a product with no sections (no/damaged `apd`) falls back to a "Description" card holding its own `description_html`, shown with its structure through `SafeHtml` (paragraphs, bold, lists, tables), starting collapsed, with a rich-text pencil. **The sections are two fixed text editors** (`SectionsEditor` in `edit/DescriptionSectionsSection.tsx`, shared with the Add product form): **Product Description** and **Product Information**, each a heading with its own rich-text editor — the titles are fixed (no title box), and there is no Add section, move, remove or Delete all. A section is created when its text is first typed (Description is always put in front of Information) and one still empty when saved is left out (`isBlankHtml`, `buildSectionsMetafield`); a section the product already has keeps its own keys, and any other section it has (a “Delivery” one) is not shown, is kept as it is and is mentioned under the editors (“1 other section on this product is kept as it is.”). The sections' pencil turns the accordion into those two editors (shown in a card while editing) with ✓ Save / ✕ Discard. Saving sends only the `apd` metafield through `PUT /products/{id}`'s `metafields` (`[{ namespace: 'apd', key: 'apd', type, value }]`, the type the metafield already has — sent exactly as the backend shows it (`json_string`) — else `json_string`; the saved text's own keys and their order are kept (it is written back from the parsed object, not the checked copy); a section added while editing gets `chosen: false` / `selected: false`, an existing one keeps its own keys): `buildSectionsMetafield` (`utils/descriptionSections.ts`) writes the whole JSON string — every other setting in it (`accordian_multi`, colours…) and each section's own extra keys are kept, `position` is renumbered from the new order — and sends nothing when no title/text/order changed (an untouched section's HTML is never re-written). **A product with no sections can get them too**: under its Description card sits a dashed **"Product description & information"** card (`NoDescriptionSections`: "No sections yet…" and an **Add sections** button — no separate pencil while nothing is being edited) that opens the same two editors; its controls are named "description sections" (`Save description sections`…) so they never clash with the Description card's own "description" pencil. - **Search highlighting**: what you searched for is marked in yellow in the rows of every list (Products, Orders, Customers, Users, Activity). `components/ui/Highlight.tsx`: a page wraps its list in `<HighlightQuery query={filters.search}>` (the search text that was sent to the API, not each keystroke), and the cells that search covers render `<Highlight text={…} />` — product name, order number / customer / email, customer and user name / email, activity summary / path. Every word of a multi-word search is marked, case-insensitive, and the text is matched as plain text (never as a pattern); it comes out as React `<mark>` elements, never as markup. The colour is the `--color-highlight` / `--color-highlight-text` tokens (yellow; a dark amber in dark mode). Use `<Highlight>` for a new searchable text cell.

The waiting files live in `productsSlice.pendingMedia` (by product id, cleared on logout), **not** in the tab, so they survive leaving the Media tab or the product, and the header counts them ("1 processing") instead of saying "No images". **Looking for them**: `usePendingMedia` checks the product every **2 s for the first 30 s**, every 4 s until 60 s, then every 16 s (a file is usually ready within seconds, and a long wait makes people add it again). **No double uploads**: `useProductMedia.add` ignores a second call while one is in flight (a ref, checked synchronously — `isAdding` only turns true on the next render), and the same address twice in one request is refused (`validateNewMedia`: "This address is already in the list above") and dropped by `buildMediaItems`. They are never dropped just because the store is slow: after 60 s the tiles read "Still waiting for the store", a notice explains that the store only accepts a direct public image link (and that Sync products brings the image in too) with a **Dismiss** button, and the product is re-read every 16 s instead of every 4 s (until 15 min, after which the tiles simply stay until dismissed). **A page refresh keeps all of this**: the waiting files (`pendingMedia`), the just-deleted images (`removedMedia`) and the created-product previews (`previewImages`) are saved to this tab's `sessionStorage` (`app/store/productMediaStorage.ts`, wired in `store.ts`: restored at startup only for a signed-in user, written on every change, validated with Zod — https addresses only — nothing older than a day, and removed when the session ends). Without it a refresh while the store was still downloading showed "No images" even though the files were on their way. The CRM only learns an image once the backend has the store's CDN copy, so until then it cannot show it; when the images do arrive, the products list is re-read too (`usePendingMedia`), because its row was read before the store had them and would otherwise keep showing no image. Both then refresh the product, list and sync status quietly (`useRefreshAfterSave`); failures show the backend's message inside the dialog, which stays open. The two calls follow the API exactly (tests replay the documented three-image example and the documented delete): `POST /products/{product_id}/media?shop=` with `{ items: [{ url, alt?, media_type }] }` (≤ 20 per call) and `DELETE /products/{product_id}/media/{attachment_id}?shop=` with no body, where `shop` is the product's store key. **Address check**: Shopify does not accept SVG, and placeholder services such as placehold.co answer with an SVG unless the address ends in `.png`/`.jpg` — so `svgImageWarning` (`utils/format.ts`) shows a warning under the preview for an `.svg` address or a placehold.co address without a raster extension (a hint only, it never blocks). **Upload from your computer** (the `FilePicker` in `AddMediaDialog`, and in Add product's Media box): a button, a drop area and `<input type=file multiple>` (`FILE_ACCEPT`) take images (JPG/JPEG, JFIF, PNG, WebP, GIF, SVG, HEIC, TIFF, BMP — under 20 MB; a `.jfif`/`.jpe` file is a JPEG and is sent as `name.jpg` with type `image/jpeg`, `forUpload`), videos (MP4, MOV, WebM — up to 1 GB) and 3D models (GLB, USDZ — up to 500 MB); `utils/mediaFiles.ts` (`checkFile`, `pickFiles`, tested) decides by the file's **extension** (browsers don't name HEIC/GLB/USDZ) and refuses the rest by file name with the reason (type, size, empty, repeats, more than 20). The 25-megapixel / 10-minute / 4K limits can't be checked reliably in the browser, so the store enforces them. Each chosen file is listed with a preview (`URL.createObjectURL`), its type and size, and a ✕. **Nothing is sent until Add to product** (or Create product). **Instant pictures — nothing waits on the upload or the store** (`hooks/useLocalMedia.ts`, `components/LocalMediaTile.tsx`, `productsSlice.localMedia`): `useAddLocalMedia().start(target, files)` makes each tile its **own** `URL.createObjectURL` preview (the picker lets go of its own when it unmounts), dispatches `localMediaAdded` (state `uploading`) so the picture is on screen the same moment, and then uploads **in the background** — it only dispatches, so closing the dialog or leaving the Add product form doesn't stop it. For each file (3 at a time, `UPLOAD_CONCURRENCY`; `uploadFileToProduct` in `useFileUpload.ts`): `POST /products/{id}/media/upload-target?shop=` (`api.products.uploadTarget`; body `{ filename, mime_type, size_bytes, media_type }` — **the request and answer are not in the spec; `readUploadTarget` in `endpoints.ts` reads the answer leniently** — so fix the body names there if the backend wants others), then `sendFileToTarget` (`lib/api/upload.ts`: a multipart POST of the target's fields **then** the file, or a PUT of the file; it uses `fetch`, **not** `apiClient`, on purpose — the address is the store's file storage and the session token must never go there — with `credentials: 'omit'` and no referrer); then **one** `POST /media` with every uploaded file's **`resource_url`** as `url`, in the order chosen (the first stays the featured image). After 60 s the tab says the store is taking longer than usual, with **Dismiss**. **A file that really fails stays on screen** with the backend's message and **Try again** (redoes only the missing step — an already-uploaded file is just attached, never uploaded twice) and **Remove**. The **Overview** shows the same previews (the main image when the product has none yet, plus a thumbnail in the row that opens the lightbox), and so does **every small picture of the product** — its row in the list (table and phone card), the quick view and the details header: `ProductImage` takes a `productId` and, while the store has no picture for the product, draws the first waiting image's own `blob:` preview (`useChosenPicture`: only an object URL this app made, never a failed file or another product's), so a new product has its picture the moment it exists; the store's own picture takes over as soon as the list has it, and the Media header counts them ("N processing"). ## Security

The browser is untrusted: real authorization lives in the backend. The frontend's job is to not leak the token, not run injected code, and fail safely. Guarded by tests in `src/config/` and `src/lib/api/client.test.ts` — keep them passing.

- **Headers** (`vercel.json`, production only): a strict Content-Security-Policy (`script-src` is `'self'` plus Google's sign-in script only — **never add `'unsafe-inline'`/`'unsafe-eval'` to scripts**), `X-Frame-Options`/`frame-ancestors` (no framing), `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS, COOP (`same-origin-allow-popups`, Google's popup needs it), CORP, `X-Permitted-Cross-Domain-Policies`, `upgrade-insecure-requests`, and `no-store` on `/api/*`. **`Content-Security-Policy-Report-Only` trials the next tightening without blocking anything**: Trusted Types and an `img-src` of Shopify's CDN only (the enforced `img-src` still allows any https address, so an image request remains a way out for injected code; read the browser console on the live site before enforcing either). A `script-src` eval violation in the console is expected: something in the bundle tries `eval` and the policy correctly refuses it. Inline _styles_ are allowed (`style-src-elem`/`style-src-attr`) only because Google's button injects them; without that the button renders unstyled. **Both CSP headers (the enforced one and the Report-Only one) end with `; report-uri /api/security/csp-report`**: the browser posts every violation to the API (the `/api` rewrite forwards it), and administrators see them in the activity log (action `csp_violation`). `securityHeaders.test.ts` locks this in. After changing the policy, load the built site with the real headers in a browser and check the console for violations (the dev server sends no CSP).
- **Developer-tools deterrent** (`lib/devToolsGuard.ts`, installed by `hooks/useDevToolsGuard.ts` from `AppProviders`; setting `VITE_BLOCK_DEVTOOLS` → `env.blockDevTools`, **on in production builds, off in `npm run dev`** unless the variable is `true`/`false`). It turns off the right-click menu and the shortcuts that open the browser's tools or the page source — **F12, Ctrl+Shift+I/J/C/K, Ctrl+U, Cmd+Option+I/J/C/U** — recognised by the physical key (`event.code`), in the capture phase so a component that stops an event can't let one slip by. **It is a deterrent, not security**: the bundle, token and every request stay readable to whoever runs the browser, and the tools open from the browser menu, `view-source:` or another browser; real protection is the backend. To keep the app usable it leaves alone everything else (Tab, arrows, Enter, Escape, Ctrl+C/V/S/F, zoom) and, **in a text field** (a text-type `input`, a `textarea`, anything `contenteditable` — the rich-text editor), the right-click menu (paste, spell-check) and **Ctrl+U, which is underline there**. `devToolsGuard.test.ts` covers the rules, `useDevToolsGuard.test.tsx` the hook, and `RichTextEditor.test.tsx` that Ctrl+U/B/I still format with the guard on. It was also checked in Edge (the real app, dev with the setting on and off, and a production build). To try it in dev put `VITE_BLOCK_DEVTOOLS=true` in `.env.local` (you will lose F12 there too). Not verified: Firefox, Safari, and whether each browser lets a page cancel its own tools' shortcuts (Chrome, Edge and Firefox do; Safari may not for Cmd+Option+I).
- **No credential in a URL** (`lib/urlSecurity.ts`). A URL is logged, kept in history and passed on in the `Referer`, so **the session is a cookie** (no script holds a token) and the sign-in code and Google's ID token only in a request body — never in a path, query or fragment. There is **no exception**, and no password-reset link exists (sign-in is an emailed code or Google). Three layers keep it true: (1) `scrubAddressBar()` runs first in `main.tsx`, before the app starts, and removes any credential-like parameter (`token`, `access_token`, `id_token`, `refresh_token`, `jwt`, `api_key`, `password`, `otp`, `session`, `sid`… — names compared in lower case without `-`/`_`; in the query **and** in the fragment, the form OAuth redirects use) from the address bar, replacing the history entry so Back doesn't bring it back and leaving every other parameter alone; (2) `apiClient`'s `request()` **refuses to send** a request whose path or `params` carry such a name (an `ApiError` with code `ERR_CREDENTIAL_IN_URL`, naming the parameter but never its value), whatever the method; (3) `config/urlTokens.test.ts` scans the source and fails if code writes `?token=…`/`#id_token=…` or builds query parameters from a credential (comments are ignored), and checks that `main.tsx` scrubs before `createRoot` and that `Bearer ${…}` appears only in `client.ts` and `endpoints.ts` (logout). A redirect to `/login` remembers only `location.pathname` in router state, never the query or fragment. The names list is exact-match (a parameter called `tag`, `code` or `key` is fine); add a name to `SENSITIVE` in `urlSecurity.ts` if the backend ever introduces another credential. Signed upload addresses the backend hands out for a file upload are not our credentials and are not built here. Checked in Edge: an address with `?token=…&Access_Token=…#id_token=…` comes out as just its other parameters, the history entry replaced.
- **No inline scripts**: the pre-paint theme script is the static file `public/theme-init.js` (a deliberate exception to "no new `.js` files" — it must be a same-origin file so the CSP can forbid inline scripts). Keep it in sync with `uiSlice.ts`.
- **No secrets in the bundle**: every `VITE_` variable is public. Never name one `*SECRET*`/`*TOKEN*`/`*KEY*`/`*PASSWORD*`; `secrets.test.ts` fails on that, on hard-coded credentials (**also in test fixtures and tracked config**: never paste a real backend response into a test — use fakes like `test-access-token`, `admin@example.com`, and no real Google client ID in `.env.example`), on `import.meta.env` outside `config/env.ts`, and on `console.*` in production code. Source maps are off (`build.sourcemap: false`).
- **Redux DevTools** are connected only in development (`devTools: env.isDev` in `store.ts`): the extension can read the whole state, the session token included.
- **The rich-text editor's raw HTML view** (`RichTextEditorView`) passes safe HTML on exactly as typed; HTML that `lib/htmlSafety.ts` (`hasUnsafeHtml`, tested: scripts, handlers, `javascript:` addresses, forms, frames other than youtube-nocookie, `style`, `svg`…) finds unsafe goes through the editor's schema first and a line says so. Saved HTML nobody changes is never touched. It guards this form only: the backend must check what it stores, and the CSV import doesn't pass through it.
- **XSS (F8)**: audited — nothing in the app puts HTML on the page as markup (no `dangerouslySetInnerHTML`/`innerHTML`/`eval`, scanned by `secrets.test.ts`). API text (customer names, notes, order notes…) is only ever rendered as text, which React escapes; images and links from data go through `safeUrl`. Where HTML has to be shown (a product's description and its sections) `SafeHtml` first runs it through **DOMPurify** (`lib/sanitizeHtml.ts`: an allow-list of the editor's tags, https pictures, YouTube-nocookie frames, http(s)/mailto/tel links, no handlers, no `javascript:`/`data:` addresses, no styles that fetch or run) and only then rebuilds it as React elements. HTML the app *sends* — `description_html` and the description sections' `content` — goes through the same `sanitizeHtml` before it leaves (create and update), because the store shows it to its customers. `sanitizeHtml.test.ts` holds the attack payloads. Use `sanitizeHtml` for any new place HTML is shown or saved; never add a raw-HTML prop. - **Safe rendering**: no `dangerouslySetInnerHTML`/`innerHTML`/`eval` (tested). API text is rendered as text; HTML descriptions go through `htmlToText`; API-supplied URLs go through `safeUrl` (http/https only) before use as `href` or `<img src>`; `target="_blank"` always has `rel="noopener noreferrer"`; third-party images send no referrer.
- **Errors**: `ApiError` carries only `status`/`data`/`code` (never the Axios request config, which holds the `Authorization` header). Users see the backend message or a friendly fallback (403/404/429/5xx/network). Render crashes show `ErrorFallback` (via `AppErrorBoundary` and the router's `RouteErrorPage`) with no technical detail in production.
- **Requests**: GETs retry twice (400 ms, 1.2 s) on network drops and 502/503/504 only; POST/PUT/PATCH/DELETE are **never** retried (a repeat could duplicate a write); timeouts, 4xx and 401 are never retried.
- **Session** (`hooks/useSessionGuard.ts`, used by `DashboardLayout`): signs out when the session passes its `expiresAt` (30 days after signing in with "Remember me", else 1 day — see "Staying signed in"), after the backend's idle limit with no activity (24 hours now), and when another tab logs out; the login page says why (`signedOutReason`). A stored session is shape-validated before use. **There is no token in the browser any more**: the session is the backend's own `HttpOnly` cookie (Axios sends `withCredentials: true`; `apiClient` adds no `Authorization` header and `logout` sends none). `localStorage` `polymer-crm:session` keeps only the user's profile and the app's expiry (a session saved by an older version, with an `accessToken`, is rewritten without it at load). On every page load `SessionBootstrap` (in `AppProviders`) calls `GET /auth/me` before drawing the app (`restoreSession` in `authSlice.ts`): 200 means signed in — the answer replaces the stored user, permissions included —, 401 means the login page, anything else (a network blip) keeps the stored user. ****Signing out of every device**: the account menu (`UserMenu`) has "Sign out other devices" (`POST /auth/logout-all?keep_this_device=true`, this device stays signed in) and "Sign out of all devices" (`POST /auth/logout-all`, this one too — the local session is cleared and the login page opens), each behind a question (`SignOutDevicesDialog`, the `signOutDevices` thunk); the CSRF token goes along like on every change. A 401 on any request while signed in** — the server really ended it (idle past its own limit, revoked, expired) — clears the user from memory (`sessionEnded`) and opens the login page with the API's own message (`signedOutMessage`; `setSessionActive` + `setUnauthorizedHandler`, which now passes the message). The server counts requests, the website's own idle timer counts mouse and keyboard, so `useSessionGuard` also calls `GET /auth/csrf` once about every 10 minutes (`KEEPALIVE_AFTER_MS`) while the person is active but the page has made no request (`lastRequestAt()` in `client.ts`) — the two timers then agree, with or without "Remember me" (which still allows 30 days, never past the idle limit). **CSRF**: every request that is not a GET/HEAD/OPTIONS carries `X-CSRF-Token` (the interceptor in `client.ts`). The token comes with the sign-in answer (`csrf_token`, kept by `api.auth.verifyOtp`/`google`) and from `GET /auth/csrf` after a reload (`restoreSession`); it lives in a module variable in `client.ts` only — never in storage, a cookie or Redux — and is cleared when the session ends. A 403 whose message mentions `X-CSRF-Token` makes `request()` fetch `/auth/csrf` again and send the change once more (the one exception to "writes are never retried": the backend refused it, so nothing was done).

## Rules

1. **Import features only through their `index.ts`.** Never `import { X } from '../../features/other/components/X.tsx'`. If it's not exported from `index.ts`, it's private to that feature.
2. **Features don't reach into each other's internals**, and avoid feature-to-feature dependencies where practical — prefer lifting shared code to `lib/`, `hooks/`, or `components/ui/`.
3. **No raw Axios/`fetch` in components or pages.** Go through a feature's `api/` module, which goes through `apiClient`.
4. **Don't add a dependency without checking this file and `package.json` first** for something that already solves the problem. The state/data/HTTP/validation/styling stack (Redux Toolkit, TanStack Query, Axios, Zod, Tailwind) is deliberately chosen — don't add a second competing library for any of those roles (no RTK Query _and_ a hand-rolled fetch hook; no a second HTTP client; no a second schema/validation library; no CSS-in-JS or CSS Modules alongside Tailwind).
5. **Server state goes through TanStack Query; client state goes through Redux.** Don't put fetched data in a Redux slice, and don't reach for `useState`/prop-drilling for something two+ unrelated components need — add a slice instead. Local component state is still the default for anything that's neither.
6. **Don't create empty placeholder directories** "for later." Add a subdirectory when the first file that belongs in it exists.
7. **Keep `App.tsx`, `main.tsx`, and `AppRouter.tsx` thin.** They wire things together; they don't contain business logic, data fetching, or complex JSX.
8. **Secrets never get committed.** Anything sensitive goes in `.env.local` (git-ignored), not `.env.example`, and never hardcoded.
9. **Type safety is not optional.** `strict` mode is on; don't add `any` or `@ts-expect-error`/`@ts-ignore` to route around a type error — fix the type. A feature's types come from its Zod schema (`z.infer`), not a hand-written `interface` duplicating it.

## What a page requests when it opens

**A page makes its requests when it is opened (a click) — only the GETs it shows, and nothing before.** No list is loaded at sign-in, hovering a sidebar link or a pagination button requests nothing, no next page is fetched on its own, the store list (`GET /shops`) is only requested on a page that shows the store dropdown (`AppBar`'s `ShopScope`), and filter-specific requests — the counts inside a filter dropdown, the Activity action choices — wait until the Filters grid is opened or the dropdown is reached for. Applying a filter asks for that filtered list (and, with the grid open, its counts). Figures above a list are read from the list's own answer, never from extra requests. The one remaining hover request is a record's **details** (the name/View button of a row), which is deliberate. `app/layouts/initialLoad.test.tsx` renders the whole shell against a fake backend that records every request and fails if a page's start-up grows.

## Mock data

A feature without a backend yet follows this pattern (Orders and Products used to; both are real now):

- `schemas/*.ts` defines a Zod schema for the shape (e.g. `orderSchema`) and derives the TS type from it (`export type Order = z.infer<typeof orderSchema>`) — the schema is the source of truth, the type is generated from it, not maintained separately.
- `api/mock*.ts` exports a `get*()` function returning a `Promise` that resolves with an array after a simulated delay (real loading states, no real network call), validated against the schema (`orderSchema.array().parse(...)`).
- `hooks/use*.ts` wraps that in TanStack Query's `useQuery` and normalizes its status to `{ data, status: 'loading' | 'success' | 'error', error }` (React Query's own status is `'pending' | 'success' | 'error'` — mapped so pages don't need to know that).
- The page renders all three states via `components/ui/Table`'s `TableState` row, not just the happy path.

**To connect a real backend**, change only what's inside `get*()` — call `apiClient` from `src/lib/api/client.ts` instead of returning mock data, `.parse()` that response against the same schema, and delete the `TODO` comment above it. The hook and page don't need to change. Follow the same `schemas/` + `api/` + `hooks/` shape for any new feature that fetches data — don't invent a different pattern per feature.

## Commands

```bash
npm run dev           # dev server
npm run dev:share     # dev server on every network interface — share http://<your-ip>:5173 (see README)
npm run build          # typecheck (tsc -b) + production build
npm run typecheck       # tsc -b only, no build output
npm run lint              # Oxlint
npm run format             # Prettier — write
npm run format:check        # Prettier — check only, no writes
npm test                     # Vitest, single run
npm run test:watch            # Vitest, watch mode
```

**Sharing the local app**: `npm run dev:share` / `npm run preview:share` run Vite with `--host`, so people on the same network can open the printed Network address; a tunnel (ngrok, Cloudflare, localtunnel) also works because `sharedHosts` in `vite.config.ts` allows those host names (Vite refuses unknown host names — add a new one there). `/api` is still proxied by the dev server, so no CORS problem. `npm run dev` stays localhost-only on purpose (it serves your source and a proxy to the real backend). Google sign-in needs the shared origin added to the client ID's authorised origins; email-code sign-in works everywhere.

Run `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, and `npm run build` before considering a change complete — all five should pass. `.github/workflows/ci.yml` runs them on every push to `main` and every pull request, plus `npm audit --omit=dev --audit-level=high`; `.github/dependabot.yml` proposes dependency updates weekly.

## Testing conventions

- Co-locate: `Foo.tsx` → `Foo.test.tsx`, in the same directory.
- Use React Testing Library queries by role/label/text (`getByRole`, `getByLabelText`) — avoid querying by class name or test-only attributes unless nothing else identifies the element.
- Anything that renders a component touching Redux, TanStack Query, or routing needs `src/test/renderWithProviders.tsx` instead of RTL's plain `render` — it wraps the tree in a **fresh** Redux store and QueryClient per call (not the app's singletons), so tests don't need to manually reset shared state between runs, plus a `MemoryRouter`.
- `vitest.config`'s `test` block lives in `vite.config.ts`; `src/test/setup.ts` registers jest-dom matchers. `globals: true` is set, so `describe`/`it`/`expect` are available without importing them (this repo's tests import them explicitly for clarity — either style works).

## Common mistakes to avoid

- Putting a feature-specific component in `components/ui/` because it "might be reused later." Wait until it actually is.
- Importing `features/x/pages/SomePage.tsx` directly from another feature or from `app/router` instead of importing it from `features/x/index.ts`.
- Calling `axios`/`fetch` directly instead of extending `lib/api/client.ts`.
- Fetching data with `useEffect` + `useState` instead of TanStack Query, or putting server data in a Redux slice instead of a query cache.
- Reaching for a second global-state approach (Context-for-everything, a new store library) instead of adding a Redux slice.
- Hand-writing a type that duplicates a Zod schema's shape instead of deriving it with `z.infer`.
- Reading `import.meta.env.VITE_*` outside `src/config/env.ts`.
- Adding a second formatter/linter (e.g. ESLint) alongside the existing Prettier/Oxlint setup.
- Adding an icon library or a new global font import — the icon set is hand-rolled in `components/ui/icons.tsx`, and `'Neue Haas Unica Pro'` (commercially licensed, not bundled) is the intended typeface; self-host a licensed webfont file rather than pulling one from a public CDN.
- Adding a `.js`/`.jsx` file, or importing with a `.js` extension that actually points at a `.ts`/`.tsx` file.
- Creating a new `ComponentName.css` file, or writing a `dark:` variant class — see "Styling" above for why neither is needed.
