# CLAUDE.md

Guidance for AI coding agents working in this repository. Read this before adding or moving files.

## What this app is

Polymer CRM surfaces a client's Shopify orders and products (and eventually inventory) in one place. **Shopify sync is a backend concern** — this frontend must never call Shopify's Admin API directly (that needs credentials that don't belong in a browser). It calls our own backend through `src/lib/api/client.ts` (Axios), which syncs with Shopify. Orders and Products currently run on mock data (`features/*/api/mock*.ts`) shaped like the eventual sync payload — see "Mock data" below.

## Stack (do not change without a strong reason)

- **React 19, Vite 8, TypeScript** (`strict: true`) — every source file is `.ts`/`.tsx`. Don't add a new `.js`/`.jsx` file.
- Package manager: **npm** (`package-lock.json` is committed — don't switch to yarn/pnpm).
- **Styling: Tailwind CSS v4** (`@tailwindcss/vite`), utility classes directly in JSX. **No per-component `.css` files and no hand-written CSS** — the only CSS file in the project is `src/styles/globals.css` (the `@import 'tailwindcss'`, the `@theme` token block, and the dark-mode variable overrides). See "Styling" below.
- Linting: **Oxlint** (`.oxlintrc.json`, with the `typescript` plugin enabled) — not ESLint.
- Formatting: **Prettier** (`.prettierrc.json`, with `prettier-plugin-tailwindcss` — it sorts class lists on format, don't hand-order them).
- Routing: **react-router-dom** (`createBrowserRouter`).
- **Server state: TanStack Query** (`@tanstack/react-query`) — every feature's `hooks/use*.ts` that fetches data wraps `useQuery`/`useMutation`, not a hand-rolled `useEffect`+`useState` fetch. The `QueryClient` lives in `src/app/queryClient.ts` and is provided in `AppProviders`.
- **Client/global state: Redux Toolkit** (`@reduxjs/toolkit` + `react-redux`) — the store is `src/app/store/store.ts`, with one slice per concern (currently just `ui`, for theme + sidebar-collapsed). Use the typed hooks in `src/app/store/hooks.ts` (`useAppDispatch`/`useAppSelector`), never the plain `react-redux` ones.
- **HTTP: Axios**, wrapped by `src/lib/api/client.ts` (`apiClient`). Never call `axios`/`fetch` directly from a feature.
- **Runtime validation: Zod** — a feature that fetches data defines a schema in `features/<name>/schemas/`, derives its TS types from that schema (`z.infer`), and validates network responses against it at the API boundary. See "Mock data" below.
- **Image lightbox: `yet-another-react-lightbox`** — the only viewer for product images (Overview gallery and Media tab, `features/products/components/ProductLightbox.tsx`). It is loaded on demand (`React.lazy`), so it and its stylesheets only download when an image is opened. Importing its three library `.css` files (in `ProductLightboxView.tsx`) is the one exception to "`globals.css` is the only CSS" — they are third-party styles, not ours. Image URLs still go through `safeUrl` (`utils/slides.ts`) and the lightbox sets `referrerPolicy: 'no-referrer'`. Don't add a second lightbox/carousel library.
- Testing: **Vitest** + **React Testing Library**, jsdom environment.

## Architecture: feature-based

```

├── main.tsx               # entry point only — no logic here
├── vite-env.d.ts            # Vite client types + ImportMetaEnv typing
├── app/                     # composition root, not a feature
│   ├── App.tsx              # AppProviders > AppRouter, nothing else
│   ├── providers/            # AppProviders.tsx — Redux + React Query providers
│   ├── store/                 # Redux: store.ts, uiSlice.ts, hooks.ts (typed dispatch/selector)
│   ├── queryClient.ts           # the app's single QueryClient
│   ├── router/                   # route table (AppRouter.tsx) + navigation.ts + NotFoundPage
│   └── layouts/                    # shared page chrome, rendered via <Outlet/>
├── features/<name>/          # one directory per business domain
│   ├── components/            # feature-only components
│   ├── hooks/                  # feature-only hooks — use*.ts wrapping useQuery/useMutation
│   ├── api/                     # this feature's requests, built on lib/api/client.ts
│   ├── schemas/                  # Zod schemas — the source of truth for this feature's types
│   ├── pages/                     # route-level components
│   ├── utils/                      # feature-local helpers
│   └── index.ts                     # PUBLIC EXPORTS — the only import surface
├── components/ui/            # generic reusable primitives (Button, Logo, StatCard,
│                              # PageHeader, Table, Badge, ThemeToggle, icons.tsx, ...)
├── hooks/                     # generic shared hooks (used by 2+ features)
├── lib/api/                    # apiClient (Axios wrapper) + ApiError
├── lib/format.ts                 # shared Intl currency/date formatters
├── config/env.ts                   # the only place import.meta.env is read
├── assets/                          # static files (logo, ...) imported by components
├── styles/globals.css                # the ONLY .css file — @theme tokens + dark-mode overrides
└── test/                              # setup.ts (jest-dom) + renderWithProviders.tsx
```

`app/router/navigation.ts` is the single list of top-level routes (path, label, icon). `NAV_ENTRIES` is what the sidebar renders: plain links plus accordion groups — currently Dashboard, then **Shopify Management** (a `NavGroup` holding Orders, Products, Customers and Inventory; closed by default, opens on click, and starts open when the current page is one of its links; see `NavAccordion.tsx`). `NAV_ITEMS` is the same routes flattened, which `AppBar` uses for the page-title heading. Add a route there, not in each component separately.

### Styling

Every component is styled with **Tailwind utility classes in `className`** — no `ComponentName.css` files, no `styled-components`, no CSS modules.

- The brand palette lives in `src/styles/globals.css` under `@theme` (`--color-accent`, `--color-text`, `--color-border`, ...). Because `@theme` declares real CSS custom properties, every Tailwind utility it generates (`bg-accent`, `text-text-muted`, `border-border`, `font-sans`, ...) compiles to `background-color: var(--color-accent)` etc — **not** a literal hex value.
- Dark mode is **not** done with Tailwind's `dark:` variant. It's done by re-declaring those same custom properties under `@media (prefers-color-scheme: dark)` and `:root[data-theme='dark']` in `globals.css` (see `src/app/store/uiSlice.ts` for how `[data-theme]` gets set). Since every color utility already resolves through `var(--color-*)`, this re-themes the whole app automatically — **don't add `dark:` variant classes anywhere**, they're redundant and will drift from the real mechanism.
- When a warning/danger/etc. tone needs a color Tailwind doesn't ship a semantic token for (e.g. a tinted background), add it to `@theme` in `globals.css` (see `--color-warning-bg`, `--color-danger-bg`) rather than hand-picking a Tailwind palette color that won't adapt for dark mode.
- For layout constants that matter exactly (sidebar width, header height), use Tailwind's arbitrary value syntax (`w-[232px]`) rather than the nearest scale step.
- A component's own file is `.tsx` only — if two or more class names always travel together, extract a local `const` (e.g. `FILTER_LABEL = '...'` in `OrdersPage.tsx`) rather than reaching for a CSS class.
- Run `npm run format` after editing className strings — `prettier-plugin-tailwindcss` sorts them into Tailwind's canonical order; don't hand-order them.

### Import extensions

`tsconfig.app.json`/`tsconfig.node.json` use `moduleResolution: "bundler"` with `allowImportingTsExtensions: true`. **Import with the real extension** (`'./Foo.tsx'`, `'./bar.ts'`), not a `.js` placeholder — that convention is for Node's `nodenext` resolution, which this project doesn't use.

## Where things go

- **New page/route** → `features/<name>/pages/`, then export it from `features/<name>/index.ts`, then add a route entry in `app/router/AppRouter.tsx` pointing at that export.
- **New feature** → create `features/<name>/` with only the subdirectories it needs (a simple feature might only need `pages/` and `index.ts` — don't scaffold empty `schemas/`/`utils/` folders in advance).
- **Data fetch** → define the shape in `features/<name>/schemas/` (Zod schema + `z.infer` type), add a function in `features/<name>/api/` that calls `apiClient` and validates the response against that schema, then a `hooks/use*.ts` that wraps it in `useQuery` (or `useMutation` for writes). Never call `apiClient`/Axios/`fetch` directly from a component. (Orders/Products currently have a `mock*.ts` in `api/` instead of a real backend call — see "Mock data" below for how to graduate one to real.)
- **New backend-facing error handling** → throw/catch `ApiError` (`src/lib/api/ApiError.ts`); check `.status`/`.data`, don't re-parse Axios errors in feature code.
- **Reusable UI with zero feature knowledge** (Button, Modal, Input, Card) → `components/ui/`. If it references a specific feature's data shape, it isn't generic — keep it in the feature.
- **Reusable hook with zero feature knowledge**, used by 2+ features → `hooks/`. Otherwise keep it inside the feature that uses it.
- **Env var** → add it to `.env.example`, declare it on `ImportMetaEnv` in `src/vite-env.d.ts`, and read it through `src/config/env.ts`. Never call `import.meta.env` from anywhere else.
- **Global client state** (something read/written from 2+ unrelated components, needs to persist, or both) → a new slice under `src/app/store/`, registered in `store.ts`'s `reducer` map. Expose it to the app through a small hook in `src/hooks/` (see `useTheme.ts`/`useSidebarCollapsed.ts`) rather than having components call `useAppSelector`/`useAppDispatch` directly everywhere — that hook is the seam if the underlying state mechanism ever changes.
- **Server state** (anything fetched from an API) → TanStack Query via a feature's `hooks/use*.ts`, not Redux. Redux is for client-owned state only.
- **New top-level route** → add it to `src/app/router/navigation.ts` (path, label, icon — inside the Shopify Management group's `items` if it's a Shopify page), then wire the route in `AppRouter.tsx`. Don't add nav links directly in `Navbar.tsx`.
- **Icon** → `src/components/ui/icons.tsx` has a small hand-written set (no icon library is installed). Add new ones there in the same stroke style rather than pulling in a dependency for one glyph. **Never use emoji as icons** — always an SVG from this file.

## Backend API (auth)

- **All real backend endpoints live in one file: `src/lib/api/endpoints.ts`** — path (`ENDPOINTS`), Zod response schema, and request function (`api.auth.requestOtp`, ...). Add new endpoints there. Its schemas live in that file (not in `features/*/schemas/`) so `lib/` never imports from a feature. Orders/Products still use their `mock*.ts` until they're moved over.
- **Auth is passwordless (email OTP) and runs on Redux Toolkit**: `src/app/store/authSlice.ts` holds the login-flow state (`step`, `email`, statuses, `error`) and the persisted `session`; `requestOtp`/`verifyOtp` are `createAsyncThunk`s that call `api.auth.*`. Components use `features/auth/hooks/useLogin.ts` (flow) and `hooks/useAuth.ts` (session/logout), never the slice directly. This is a deliberate exception to "server state → TanStack Query": a login flow is client-owned state, not a cached resource. The backend rate-limits code requests per account (429 "Please wait N seconds…"): that means a code was already sent and is still valid, so `requestOtp` resolves as `rateLimited` — the flow moves to the code screen with the backend's message and a resend timer of exactly N seconds (`resendAvailableAt`, parsed by `parseWaitSeconds`) instead of stranding the user on an error. A 429 without a readable wait time is still shown as an error.
- **Google sign-in** (`POST /auth/google`) sends the Google ID token; `features/auth/utils/googleIdentity.ts` loads Google's GIS script (no npm package) and `GoogleSignIn.tsx` renders Google's own button. It needs `VITE_GOOGLE_CLIENT_ID`; when empty, production hides the Google option and development shows a disabled placeholder with setup instructions. The thunk is `googleSignIn` in `authSlice.ts`.
- **Products** (`GET /products`) is real-API and lives in Redux: `src/app/store/productsSlice.ts` holds the filters, a per-query page cache (stale-while-revalidate, 30s), the previous results shown while the next query loads, accumulated filter options, recently-opened products and the open product. `features/products/hooks/useProducts.ts` is the only consumer; `DashboardLayout` calls `usePrefetchProducts()` so the list is cached before the page opens, and the next page is prefetched so paging is instant. This is a deliberate exception to "server state → TanStack Query" (Orders still use TanStack Query + mock data). The cache is cleared on logout/expired session.
- **Product details** (`GET /products/{id}`, UUID or Shopify ID — not the handle) render in the _same page_ at `/products/:id` (route `products/*` → `ProductsPage`), never in a slide-over. Opening is only via the product name, the View button or the mobile card (not the rest of the row). Clicking a row's _image_ instead opens a right-hand quick-view panel (`ProductQuickView`, local state in `ProductsPage`) built from the already-loaded list row, with an "Open full details" button. In the Overview tab the left column shows the main image plus a single scrolling row (`components/ui/ScrollRow.tsx`, with arrows that appear only when there is more to scroll) of a thumbnail of every product image; clicking any of them (or "View Full", or an image on the Media tab) opens the lightbox. "Status & Launch" and "Description" start collapsed (`defaultOpen={false}`); "Product Specifications" starts open. The page keeps a strip of open-product **tabs** (`tabs` in `productsSlice`). Details are cached in the slice (`details`); hovering the name or View prefetches them, and the header draws from the already-loaded list row (`preview`) while the rest loads. The large Shopify `raw_json` is requested only when the "Raw data" tab opens (`include_raw=true`, cached separately). Product description HTML is only ever shown as plain text (`htmlToText`) and links go through `safeUrl`.
- **Customers** (`GET /customers`) is a sidebar page at `/customers` (entry in `navigation.ts`), built exactly like the products list: `src/app/store/customersSlice.ts` (filters, per-query cache with stale-while-revalidate, previous results while loading, next-page prefetch, cleared on logout), `features/customers/hooks/useCustomers.ts` as the only consumer, and `usePrefetchCustomers()` called from `DashboardLayout` so the list is cached before the page opens. **Customer details** (`GET /customers/{id}`, UUID, Shopify ID or email) render in the _same page_ at `/customers/:id` (route `customers/*` → `CustomersPage`), opened only via the View button/card; the list stays mounted but hidden. Details are cached in the slice (`details`), hovering View prefetches them, and the header/summary draw from the already-loaded list row (`preview`) while the rest loads. The large Shopify `raw_json` is requested only when the "Raw data" tab opens (`include_raw=true`, cached separately). Generic pieces shared with Products live in `components/ui` (`Pagination`, `PaginationFooter`, `SelectField`, `CopyButton`, and `DetailSection` with its `Field`/`DetailTable`/`DetailEmpty`/`DetailSkeleton`/`RawJsonPanel` details-page building blocks), `hooks/` (`useDebouncedField`, `useMediaQuery`) and `lib/format.ts` — reuse them rather than copying.
- **Shop (store) dropdown** — the backend serves several Shopify stores. `GET /shops` lists the ones the signed-in user may see (in dropdown order; admins see all), and `shop=<key or domain>` (empty or `all` = every store) narrows `/products`, `/customers`, `/orders` and their detail/sync calls. The top-bar dropdown (`app/layouts/ShopSwitcher.tsx`, driven by `hooks/useShops.ts`) is global client state in `app/store/shopSlice.ts`; it defaults to **All shops** every visit (not persisted) and is cleared on logout. `productsSlice`/`customersSlice` listen for `shopSelected`, set `filters.shop`, go back to page 1 and send `shop` on the list _and_ the status-tab count queries (so each store is cached separately); "Clear all" keeps the chosen store. The dropdown only shows on pages whose `NAV_ITEMS` entry has `shopScoped: true` (currently Products and Customers) — set that flag when you make another page (e.g. Orders, once it leaves mock data) send `shop`, don't show the dropdown on a page that ignores it. Details by UUID don't need `shop`.
- **Users** (`GET /users`, `POST /users`, `GET /roles`) is a top-level sidebar page named **User Management** at `/users` (below the Shopify Management group; it isn't a Shopify page and isn't `shopScoped`). It is plain server data, so it uses **TanStack Query** (not a Redux slice): `features/users/hooks/useUsers.ts` holds the filters (search, role, status, page, page size) in local state and wraps `useQuery` with `keepPreviousData`; `useRoles` (roles feed the role filter and the form; cached 5 min) and `useCreateUser` (`useMutation`, invalidates `['users']` on success; writes are never auto-retried) sit beside it. The list reuses `PaginationFooter` and the same table/card/skeleton/empty/error pattern as Customers. **Add user** opens `components/ui/SidePanel.tsx` (generic slide-over: Escape/backdrop/✕, focus in and back) holding `UserFormPanel` — first name + email required, last name/phone optional, role from `/roles` (defaults to `office`), and store access (`shop_keys`) checkboxes from `/shops` that only apply to non-admin roles (`ADMIN_ROLE` = `admin`; admins send `[]`). Staff have no password — they sign in by emailed code or Google. `FormMessage` lives in `components/ui` (shared by login and this form). Users' own access to the page is enforced by the backend (a 403 shows its message); the sidebar doesn't hide the link yet.
- **Activity** (`GET /activity`, `GET /activity/actions`) is the top-level **Activity Management** page at `/activity` — the audit log of what staff did (who, what, when, IP/device, status, duration, plus free-form `details`/`changes` JSON). Plain server data, so **TanStack Query**: `features/activity/hooks/activityQueries.ts` holds the filters (search, user, action, method, entity type/id, from/to, page, size → API params, `datetime-local` converted to ISO) and the shared `queryOptions`; `useActivity` wraps `useQuery` with `keepPreviousData`, a 30 s `staleTime`, and prefetches the next page (only once the _current_ query's own `has_next` is known — never from placeholder data). **Instant loading**: every query is cached, and `usePrefetchActivity` (called from the sidebar link's hover/focus in `Navbar` via `NavItemLink`'s `onPrefetch`) loads the first page + action list before the click. It is deliberately _not_ run at sign-in because the backend logs every request into this very log (and non-admins would just get 403s). Dropdowns: actions (with counts) from `/activity/actions`, users from `/users?page_size=100` (falls back to the users seen in the rows if that is forbidden). **Security**: the whole TanStack cache is cleared when the session ends (`store.ts` → `queryClient.clear()`); queries don't retry 4xx (`app/queryClient.ts` `shouldRetry`) so a 403 isn't re-logged; `details`/`changes`/summary are only ever rendered as text (JSON in a `<pre>`), never as markup; filter inputs are length-limited and sent via axios `params` (URL-encoded); a backwards date range disables the query. The details slide-over is `SidePanel` (`wide`). Reuses `PaginationFooter` and the same toolbar/table/card/skeleton/empty/error pattern as Customers.
- **Tab counts (every list page)**: a segmented tab strip (Products/Users status, Customers role, Activity method) shows a count on _every_ tab, not just the open one. Each count is its own cached one-row query (`page_size=1`, read `total`) with the other narrowing filters applied but that tab's value swapped in — Products/Customers via a `…CountFilters` helper in the slice + `useProductStatusCounts`/`useCustomerRoleCounts` (Redux cache), Users/Activity via `useQueries` in `useUserStatusCounts`/`useActivityMethodCounts` (same query-key family as the list, so a create/refresh updates them). The open tab falls back to the list's own `total` while its count loads. When adding a tab strip, do the same; in tests, tab buttons are named like "POST 96" (match with `/^POST/`), and count requests are `page_size === 1` (exclude them when counting page requests).
- **Product editing** (`PUT /products/{id}?shop=`, plus `POST …/push` and `GET …/sync`) — every endpoint, schema and body type (`ProductUpdateBody`, `ProductVariantInput`, …) is in `endpoints.ts`. There are two ways in. **On the details page, editing is in place, section by section — no dialog and no global Edit button**: every editable section has its own pencil (Product Specifications, Status & Launch, Description, SEO & Online Store cards; the Variants, Collections and Media tabs). Clicking it turns _that section only_ into its fields (`components/edit/EditableSection.tsx`: `EditableCard` for header-slot cards via `DetailSection`'s `actions`, `EditableTab` for whole tabs, driven by `hooks/useSectionEdit.ts`), and the pencil becomes two icon buttons — ✓ **Save** and ✕ **Discard** (`components/ui/IconAction.tsx`: icon-only, each names itself in a CSS tooltip on hover/focus). Escape also discards. A tab can replace the default pencil-only toolbar with its own header row via `EditableTab`'s `header` prop — the **Collections** tab does: one row with "In 10 collections" + a badge per type, the filter box, the pencil and an **Add collection** button. While editing, the row shows Save/Discard and the "Add to a collection by ID" box stays hidden until **Add collection** is clicked (clicking again tucks it away); the box then sits on top of the list, with the collections about to be added listed before the existing ones. Clicking Add collection from the read-only view starts editing with the box already open and focused. Each section keeps its own draft and sends only its own changes, so saving the specifications never touches the variants, and several sections can be open at once; validation is scoped to the section (`errorPrefixes`). In the **list**, the pencil in each row ("Actions" column, beside the eye) still opens `ProductEditPanel`, a wide `SidePanel` quick-edit of everything: Basics, Tags, Search listing (SEO), Variants & prices, Images & media, Collections. The API takes _any subset_ of fields, so `utils/editDraft.ts` turns the form into the **smallest** body (`buildUpdateBody`: only changed fields, tags/collections as add/remove diffs, per-variant changed fields, media update/remove/order/add) and validates with the API's limits (`validateDraft`); the diff is taken against a _frozen snapshot from when the form opened_, so an edit never reverts a colleague's change to a field you didn't touch. **Instant, no loader**: hovering the pencil/Edit prefetches the details, so the form opens populated on the first frame (`useProductForEdit` — unlike `useProductDetails` it opens no tab; the in-place editors need no fetch at all, they edit the details already on the page). When the server confirms a save, `updateProduct.fulfilled` in `productsSlice` patches every cached copy at once (list rows, `lastData`, details, tab labels; helpers in `app/store/productPatch.ts`) and marks them stale; `useSaveProduct` then refetches the authoritative copy quietly (old values stay visible meanwhile) and refreshes the tab counts if the status changed. An edit is saved in the CRM at once and pushed to the store right after, so a saved product's header shows `ProductSyncStatus` (polls `GET …/sync` while in progress, "Retry" calls `POST …/push` after a failure; TanStack Query, `useProductSync`) — only for products edited this session, so merely viewing a product costs no extra request. Status can only be set to Active/Draft/Archived (the API has no "unlisted"). Adding to a collection is by CRM collection ID (no list-collections endpoint yet). Sibling elements in a page need distinct `key`s (`details-…`, `edit-…`, `quick-view-…`): a shared key duplicates elements.
- The API has no endpoint listing vendors/types/tags/countries, so those dropdowns fill from items seen so far (`facets`); a backend facets endpoint would make them exact.
- **Routes**: everything under `DashboardLayout` is behind `ProtectedRoute`; a 401 on an authenticated request clears the session (`setUnauthorizedHandler` in `lib/api/client.ts`) and the guard redirects to `/login`. Below 768px the sidebar always renders as its icon rail.
- Error messages shown to users come from the backend: `lib/api/client.ts` turns a failed response into an `ApiError` whose `message` is the first field error (422) or the body's `message`, with a friendly fallback for network failures/timeouts.
- The backend rejects browser CORS from localhost, so dev/preview proxy `/api` to `https://polymeruk-api.vercel.app` (see `vite.config.ts`). On Vercel, `vercel.json` does the same job: it rewrites `/api/*` to the backend (without it every API call 404s), serves `index.html` for deep links like `/products/<id>`, and marks `/api/*` responses `no-store`. `VITE_API_BASE_URL=/api` (the default) sends requests through that rewrite, so the browser's Network tab shows your own domain's `/api/...` — that is the proxy, not a bug. Setting it to the full backend URL (`https://polymeruk-api.vercel.app/api`) makes the browser call the backend directly instead; the CSP `connect-src` in `vercel.json` already allows that host. Direct mode only works on origins in the backend's CORS list (currently just `https://polymer-frontend.vercel.app`: previews, other domains and localhost get blocked) and adds a CORS preflight per distinct authenticated URL, so the proxy is the default. Keep `/api` in `.env.local` for local development.

## Security

The browser is untrusted: real authorization lives in the backend. The frontend's job is to not leak the token, not run injected code, and fail safely. Guarded by tests in `src/config/` and `src/lib/api/client.test.ts` — keep them passing.

- **Headers** (`vercel.json`, production only): a strict Content-Security-Policy (`script-src` is `'self'` plus Google's sign-in script only — **never add `'unsafe-inline'`/`'unsafe-eval'` to scripts**), `X-Frame-Options`/`frame-ancestors` (no framing), `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS, and `no-store` on `/api/*`. Inline _styles_ are allowed (`style-src-elem`/`style-src-attr`) only because Google's button injects them; without that the button renders unstyled. `securityHeaders.test.ts` locks this in. After changing the policy, load the built site with the real headers in a browser and check the console for violations (the dev server sends no CSP).
- **No inline scripts**: the pre-paint theme script is the static file `public/theme-init.js` (a deliberate exception to "no new `.js` files" — it must be a same-origin file so the CSP can forbid inline scripts). Keep it in sync with `uiSlice.ts`.
- **No secrets in the bundle**: every `VITE_` variable is public. Never name one `*SECRET*`/`*TOKEN*`/`*KEY*`/`*PASSWORD*`; `secrets.test.ts` fails on that, on hard-coded credentials, on `import.meta.env` outside `config/env.ts`, and on `console.*` in production code. Source maps are off (`build.sourcemap: false`).
- **Safe rendering**: no `dangerouslySetInnerHTML`/`innerHTML`/`eval` (tested). API text is rendered as text; HTML descriptions go through `htmlToText`; API-supplied URLs go through `safeUrl` (http/https only) before use as `href` or `<img src>`; `target="_blank"` always has `rel="noopener noreferrer"`; third-party images send no referrer.
- **Errors**: `ApiError` carries only `status`/`data`/`code` (never the Axios request config, which holds the `Authorization` header). Users see the backend message or a friendly fallback (403/404/429/5xx/network). Render crashes show `ErrorFallback` (via `AppErrorBoundary` and the router's `RouteErrorPage`) with no technical detail in production.
- **Requests**: GETs retry twice (400 ms, 1.2 s) on network drops and 502/503/504 only; POST/PUT/PATCH/DELETE are **never** retried (a repeat could duplicate a write); timeouts, 4xx and 401 are never retried.
- **Session** (`hooks/useSessionGuard.ts`, used by `DashboardLayout`): signs out after 30 min without interaction in any tab, at token expiry, and when another tab logs out; the login page says why (`signedOutReason`). A stored session is shape-validated before use. The token itself still lives in `localStorage` (readable by any script that runs on the page — the CSP is the mitigation); an `HttpOnly` cookie session would need a backend change.

## Rules

1. **Import features only through their `index.ts`.** Never `import { X } from '../../features/other/components/X.tsx'`. If it's not exported from `index.ts`, it's private to that feature.
2. **Features don't reach into each other's internals**, and avoid feature-to-feature dependencies where practical — prefer lifting shared code to `lib/`, `hooks/`, or `components/ui/`.
3. **No raw Axios/`fetch` in components or pages.** Go through a feature's `api/` module, which goes through `apiClient`.
4. **Don't add a dependency without checking this file and `package.json` first** for something that already solves the problem. The state/data/HTTP/validation/styling stack (Redux Toolkit, TanStack Query, Axios, Zod, Tailwind) is deliberately chosen — don't add a second competing library for any of those roles (no RTK Query _and_ a hand-rolled fetch hook; no a second HTTP client; no a second schema/validation library; no CSS-in-JS or CSS Modules alongside Tailwind).
5. **Server state goes through TanStack Query; client state goes through Redux.** Don't put fetched data in a Redux slice, and don't reach for `useState`/prop-drilling for something two+ unrelated components need — add a slice instead. Local component state is still the default for anything that's neither.
6. **Don't create empty placeholder directories** "for later." Add a subdirectory when the first file that belongs in it exists.
7. **Keep `App.tsx`, `main.tsx`, and `AppRouter.tsx` thin.** They wire things together; they don't contain business logic, data fetching, or complex JSX.
8. **Secrets never get committed.** Anything sensitive goes in `.env.local` (git-ignored), not `.env.example`, and never hardcoded.
9. **Type safety is not optional.** `strict` mode is on; don't add `any` or `@ts-expect-error`/`@ts-ignore` to route around a type error — fix the type. A feature's types come from its Zod schema (`z.infer`), not a hand-written `interface` duplicating it.

## Mock data

`features/orders/` and `features/products/` follow this pattern for data that doesn't have a real backend yet:

- `schemas/*.ts` defines a Zod schema for the shape (e.g. `orderSchema`) and derives the TS type from it (`export type Order = z.infer<typeof orderSchema>`) — the schema is the source of truth, the type is generated from it, not maintained separately.
- `api/mock*.ts` exports a `get*()` function returning a `Promise` that resolves with an array after a simulated delay (real loading states, no real network call), validated against the schema (`orderSchema.array().parse(...)`).
- `hooks/use*.ts` wraps that in TanStack Query's `useQuery` and normalizes its status to `{ data, status: 'loading' | 'success' | 'error', error }` (React Query's own status is `'pending' | 'success' | 'error'` — mapped so pages don't need to know that).
- The page renders all three states via `components/ui/Table`'s `TableState` row, not just the happy path.

**To connect a real backend**, change only what's inside `get*()` — call `apiClient` from `src/lib/api/client.ts` instead of returning mock data, `.parse()` that response against the same schema, and delete the `TODO` comment above it. The hook and page don't need to change. Follow the same `schemas/` + `api/` + `hooks/` shape for any new feature that fetches data — don't invent a different pattern per feature.

## Testing conventions

- Co-locate: `Foo.tsx` → `Foo.test.tsx`, in the same directory.
- Use React Testing Library queries by role/label/text (`getByRole`, `getByLabelText`) — avoid querying by class name or test-only attributes unless nothing else identifies the element.
- Anything that renders a component touching Redux, TanStack Query, or routing needs `src/test/renderWithProviders.tsx` instead of RTL's plain `render` — it wraps the tree in a **fresh** Redux store and QueryClient per call (not the app's singletons), so tests don't need to manually reset shared state between runs, plus a `MemoryRouter`.
- `vitest.config`'s `test` block lives in `vite.config.ts`; `src/test/setup.ts` registers jest-dom matchers. `globals: true` is set, so `describe`/`it`/`expect` are available without importing them (this repo's tests import them explicitly for clarity — either style works).

## Common mistakes to avoid

- Putting a feature-specific component in `components/ui/` because it "might be reused later." Wait until it actually is.
- Importing `features/x/pages/SomePage.tsx` directly from another feature or from `app/router` instead of importing it from `features/x/index.ts`.
- Calling `axios`/`fetch` directly instead of extending `lib/api/client.ts`.
- Fetching data with `useEffect` + `useState` instead of TanStack Query, or putting server data in a Redux slice instead of a query cache.
- Reaching for a second global-state approach (Context-for-everything, a new store library) instead of adding a Redux slice.
- Hand-writing a type that duplicates a Zod schema's shape instead of deriving it with `z.infer`.
- Reading `import.meta.env.VITE_*` outside `src/config/env.ts`.
- Adding a second formatter/linter (e.g. ESLint) alongside the existing Prettier/Oxlint setup.
- Adding an icon library or a new global font import — the icon set is hand-rolled in `components/ui/icons.tsx`, and `'Neue Haas Unica Pro'` (commercially licensed, not bundled) is the intended typeface; self-host a licensed webfont file rather than pulling one from a public CDN.
- Adding a `.js`/`.jsx` file, or importing with a `.js` extension that actually points at a `.ts`/`.tsx` file.
- Creating a new `ComponentName.css` file, or writing a `dark:` variant class — see "Styling" above for why neither is needed.
