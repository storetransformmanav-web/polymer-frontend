# CLAUDE.md

Guidance for AI coding agents working in this repository. Read this before adding or moving files.

## What this app is

Polymer CRM surfaces a client's Shopify orders and products (and eventually inventory) in one place. **Shopify sync is a backend concern** — this frontend must never call Shopify's Admin API directly (that needs credentials that don't belong in a browser). It calls our own backend through `src/lib/api/client.ts` (Axios), which syncs with Shopify. Products, Customers and Orders read the real backend; no feature runs on mock data any more — the "Mock data" pattern below is kept as a recipe for a new feature that has no backend yet.

## Stack (do not change without a strong reason)

- **React 19, Vite 8, TypeScript** (`strict: true`) — every source file is `.ts`/`.tsx`. Don't add a new `.js`/`.jsx` file.
- Package manager: **npm** (`package-lock.json` is committed — don't switch to yarn/pnpm).
- **Styling: Tailwind CSS v4** (`@tailwindcss/vite`), utility classes directly in JSX. **No per-component `.css` files and no hand-written CSS** — the only CSS file in the project is `src/styles/globals.css` (the `@import 'tailwindcss'`, the `@theme` token block, and the dark-mode variable overrides). See "Styling" below.
- Linting: **Oxlint** (`.oxlintrc.json`, with the `typescript` plugin enabled) — not ESLint.
- Formatting: **Prettier** (`.prettierrc.json`, with `prettier-plugin-tailwindcss` — it sorts class lists on format, don't hand-order them).
- Routing: **react-router-dom** (`createBrowserRouter`).
- **Server state: TanStack Query** (`@tanstack/react-query`) — every feature's `hooks/use*.ts` that fetches data wraps `useQuery`/`useMutation`, not a hand-rolled `useEffect`+`useState` fetch. The `QueryClient` lives in `src/app/queryClient.ts` and is provided in `AppProviders`.
- **Client/global state: Redux Toolkit** (`@reduxjs/toolkit` + `react-redux`) — the store is `src/app/store/store.ts`, with one slice per concern (currently just `ui`, for theme + sidebar-collapsed). Use the typed hooks in `src/app/store/hooks.ts` (`useAppDispatch`/`useAppSelector`), never the plain `react-redux` ones.
- **HTTP: Axios**, wrapped by `src/lib/api/client.ts` (`apiClient`). Never call `axios`/`fetch` directly from a feature.
- **Runtime validation: Zod** — a feature that fetches data defines a schema in `features/<name>/schemas/`, derives its TS types from that schema (`z.infer`), and validates network responses against it at the API boundary. See "Mock data" below.
- **Image lightbox: `yet-another-react-lightbox`** — the only viewer for product images (Overview gallery and Media tab, `features/products/components/ProductLightbox.tsx`). It is loaded on demand (`React.lazy`), so it and its stylesheets only download when an image is opened. Importing its three library `.css` files (in `ProductLightboxView.tsx`) is the one exception to "`globals.css` is the only CSS" — they are third-party styles, not ours. Image URLs still go through `safeUrl` (`utils/slides.ts`) and the lightbox sets `referrerPolicy: 'no-referrer'`. Don't add a second lightbox/carousel library.
- **Rich-text editor: TipTap** (`@tiptap/react` + `starter-kit` and the text-style/colour, text-align, image, table and YouTube extensions) — the only editor for HTML content, used for a product's description (`components/ui/RichTextEditor.tsx`). It is loaded on demand (`React.lazy`, chunk entry in `richTextEditorChunk.ts`; `preloadRichTextEditor` runs when the pointer reaches the Description pencil, so it is normally there by the click), so it only downloads when an editor is shown. Don't add a second editor library. Its schema is what keeps HTML safe (see "Safe rendering").
- Testing: **Vitest** + **React Testing Library**, jsdom environment.

## Architecture: feature-based

```
src/
├── main.tsx               # entry point only — no logic here
├── vite-env.d.ts            # Vite client types + ImportMetaEnv typing
├── app/                     # composition root, not a feature
│   ├── App.tsx              # AppProviders > AppRouter, nothing else
│   ├── providers/            # AppProviders.tsx — Redux + React Query providers
│   ├── store/                 # Redux: store.ts, uiSlice.ts, hooks.ts (typed dispatch/selector)
│   ├── queryClient.ts           # the app's single QueryClient
│   ├── router/                   # route table (AppRouter.tsx) + navigation.ts + NotFoundPage
│   └── layouts/                    # shared page chrome, rendered via <Outlet/>
├── features/<name>/          # one directory per business domain
│   ├── components/            # feature-only components
│   ├── hooks/                  # feature-only hooks — use*.ts wrapping useQuery/useMutation
│   ├── api/                     # this feature's requests, built on lib/api/client.ts
│   ├── schemas/                  # Zod schemas — the source of truth for this feature's types
│   ├── pages/                     # route-level components
│   ├── utils/                      # feature-local helpers
│   └── index.ts                     # PUBLIC EXPORTS — the only import surface
├── components/ui/            # generic reusable primitives (Button, Logo, StatCard,
│                              # PageHeader, Table, Badge, ThemeToggle, icons.tsx, ...)
├── hooks/                     # generic shared hooks (used by 2+ features)
├── lib/api/                    # apiClient (Axios wrapper) + ApiError
├── lib/format.ts                 # shared Intl currency/date formatters
├── config/env.ts                   # the only place import.meta.env is read
├── assets/                          # static files (logo, ...) imported by components
├── styles/globals.css                # the ONLY .css file — @theme tokens + dark-mode overrides
└── test/                              # setup.ts (jest-dom) + renderWithProviders.tsx
```

`app/router/navigation.ts` is the single list of top-level routes (path, label, icon). `NAV_ENTRIES` is what the sidebar renders: plain links plus accordion groups — currently Dashboard, then **Shopify Management** (a `NavGroup` holding Orders, Products, Customers and Inventory; closed by default, opens on click, and starts open when the current page is one of its links; see `NavAccordion.tsx`). **In the icon rail (sidebar closed) a group is just its icon, and clicking it opens a card to the right of the rail** (`NavGroupFlyout.tsx`: the group's name in small capitals, then each page with its icon and label, the current page tinted; portalled and fixed to the screen, closes on Escape, an outside click, choosing a page, scroll or resize) — any group with several pages gets this automatically. `NAV_ITEMS` is the same routes flattened, which `AppBar` uses for the page-title heading. Add a route there, not in each component separately.

### Styling

**Text size is one scale for every page**: `html { font-size: 93.75% }` in `globals.css` (15px root, not 16px). Type and spacing are in `rem`, so this shrinks every page together — change that one number to resize the whole app; don't set a different size on a page.

Every component is styled with **Tailwind utility classes in `className`** — no `ComponentName.css` files, no `styled-components`, no CSS modules.

- The brand palette lives in `src/styles/globals.css` under `@theme` (`--color-accent`, `--color-text`, `--color-border`, ...). Because `@theme` declares real CSS custom properties, every Tailwind utility it generates (`bg-accent`, `text-text-muted`, `border-border`, `font-sans`, ...) compiles to `background-color: var(--color-accent)` etc — **not** a literal hex value.
- Dark mode is **not** done with Tailwind's `dark:` variant. It's done by re-declaring those same custom properties under `@media (prefers-color-scheme: dark)` and `:root[data-theme='dark']` in `globals.css` (see `src/app/store/uiSlice.ts` for how `[data-theme]` gets set). Since every color utility already resolves through `var(--color-*)`, this re-themes the whole app automatically — **don't add `dark:` variant classes anywhere**, they're redundant and will drift from the real mechanism.
- When a warning/danger/etc. tone needs a color Tailwind doesn't ship a semantic token for (e.g. a tinted background), add it to `@theme` in `globals.css` (see `--color-warning-bg`, `--color-danger-bg`) rather than hand-picking a Tailwind palette color that won't adapt for dark mode.
- For layout constants that matter exactly (sidebar width, header height), use Tailwind's arbitrary value syntax (`w-[232px]`) rather than the nearest scale step.
- A component's own file is `.tsx` only — if two or more class names always travel together, extract a local `const` (e.g. `FILTER_LABEL = '...'` in `OrdersPage.tsx`) rather than reaching for a CSS class.
- Run `npm run format` after editing className strings — `prettier-plugin-tailwindcss` sorts them into Tailwind's canonical order; don't hand-order them.

**Details-page cards** have a sage-green border by default (`DETAIL_CARD` in `DetailSection.tsx`: `border-border-strong`, `#b4c9b8`; dividers inside use it too). The hover colour is on the **title row only**, never the whole card: a `DetailSection`'s header row and each `DescriptionAccordion` row take `hover:bg-accent-tint/60` (the same tint as a hovered table row). Don't add a hover border to a whole card.

### Import extensions

`tsconfig.app.json`/`tsconfig.node.json` use `moduleResolution: "bundler"` with `allowImportingTsExtensions: true`. **Import with the real extension** (`'./Foo.tsx'`, `'./bar.ts'`), not a `.js` placeholder — that convention is for Node's `nodenext` resolution, which this project doesn't use.

## Where things go

- **New page/route** → `features/<name>/pages/`, then export it from `features/<name>/index.ts`, then add a route entry in `app/router/AppRouter.tsx` pointing at that export.
- **New feature** → create `features/<name>/` with only the subdirectories it needs (a simple feature might only need `pages/` and `index.ts` — don't scaffold empty `schemas/`/`utils/` folders in advance).
- **Data fetch** → define the shape in `features/<name>/schemas/` (Zod schema + `z.infer` type), add a function in `features/<name>/api/` that calls `apiClient` and validates the response against that schema, then a `hooks/use*.ts` that wraps it in `useQuery` (or `useMutation` for writes). Never call `apiClient`/Axios/`fetch` directly from a component. (A feature with no backend yet uses a `mock*.ts` in `api/` instead of a real backend call — see "Mock data" below for how to graduate it to real.)
- **New backend-facing error handling** → throw/catch `ApiError` (`src/lib/api/ApiError.ts`); check `.status`/`.data`, don't re-parse Axios errors in feature code.
- **Reusable UI with zero feature knowledge** (Button, Modal, Input, Card) → `components/ui/`. If it references a specific feature's data shape, it isn't generic — keep it in the feature.
- **Reusable hook with zero feature knowledge**, used by 2+ features → `hooks/`. Otherwise keep it inside the feature that uses it.
- **Env var** → add it to `.env.example`, declare it on `ImportMetaEnv` in `src/vite-env.d.ts`, and read it through `src/config/env.ts`. Never call `import.meta.env` from anywhere else.
- **Global client state** (something read/written from 2+ unrelated components, needs to persist, or both) → a new slice under `src/app/store/`, registered in `store.ts`'s `reducer` map. Expose it to the app through a small hook in `src/hooks/` (see `useTheme.ts`/`useSidebarCollapsed.ts`) rather than having components call `useAppSelector`/`useAppDispatch` directly everywhere — that hook is the seam if the underlying state mechanism ever changes.
- **Server state** (anything fetched from an API) → TanStack Query via a feature's `hooks/use*.ts`, not Redux. Redux is for client-owned state only.
- **New top-level route** → add it to `src/app/router/navigation.ts` (path, label, icon — inside the Shopify Management group's `items` if it's a Shopify page), then wire the route in `AppRouter.tsx`. Don't add nav links directly in `Navbar.tsx`.
- **Icon** → `src/components/ui/icons.tsx` has a small hand-written set (no icon library is installed). Add new ones there in the same stroke style rather than pulling in a dependency for one glyph. **Never use emoji as icons** — always an SVG from this file.

## Backend API (auth)

- **All real backend endpoints live in one file: `src/lib/api/endpoints.ts`** — path (`ENDPOINTS`), Zod response schema, and request function (`api.auth.requestOtp`, ...). Add new endpoints there. Its schemas live in that file (not in `features/*/schemas/`) so `lib/` never imports from a feature.
- **Auth is passwordless (email OTP) and runs on Redux Toolkit**: `src/app/store/authSlice.ts` holds the login-flow state (`step`, `email`, statuses, `error`) and the persisted `session`; `requestOtp`/`verifyOtp` are `createAsyncThunk`s that call `api.auth.*`. Components use `features/auth/hooks/useLogin.ts` (flow) and `hooks/useAuth.ts` (session/logout), never the slice directly. This is a deliberate exception to "server state → TanStack Query": a login flow is client-owned state, not a cached resource. The backend rate-limits code requests per account (429 "Please wait N seconds…"): that means a code was already sent and is still valid, so `requestOtp` resolves as `rateLimited` — the flow moves to the code screen with the backend's message and a resend timer of exactly N seconds (`resendAvailableAt`, parsed by `parseWaitSeconds`) instead of stranding the user on an error. A 429 without a readable wait time is still shown as an error.
- **Staying signed in**: there is no "Remember me" choice — **every sign-in lasts 30 days, and nothing signs you out sooner except Log out** (no inactivity timeout). The backend issues 30-day tokens (`expires_at`); `sessionExpiry` (authSlice) sets the session's `expiresAt` to the sooner of that and now + 30 days. The sign-in calls (`POST /auth/otp/verify` and `POST /auth/google`) always send **`remember_me: true`** (`STAY_SIGNED_IN` in `endpoints.ts`): the backend now issues a 30-day token only with it (`true` = 30 days; its default `false` = 1 day), so leaving it out would sign everyone out after a day. The answer's `user.permissions` (access by area: `{ products: { view, manage }, … }`) is kept with the session but nothing is hidden by it yet. When it passes, `useSessionGuard` signs out with `logout('expired')`, which also revokes the token, and the login page says the session has expired (`SignOutReason` is just `'expired'`). A session removed in another tab (logout there) signs out here too.
- **Google sign-in** (`POST /auth/google`) sends the Google ID token; `features/auth/utils/googleIdentity.ts` loads Google's GIS script (no npm package) and `GoogleSignIn.tsx` renders Google's own button. It needs `VITE_GOOGLE_CLIENT_ID`; when empty, production hides the Google option and development shows a disabled placeholder with setup instructions. The thunk is `googleSignIn` in `authSlice.ts`.
- **Products** (`GET /products`) is real-API and lives in Redux: `src/app/store/productsSlice.ts` holds the filters, a per-query page cache (stale-while-revalidate, 30s), the previous results shown while the next query loads, accumulated filter options, recently-opened products and the open product. `features/products/hooks/useProducts.ts` is the only consumer; The list loads when the page is opened (a click on its sidebar link) — **not at sign-in, not when the link is hovered, and no next page ahead of time**; a page is requested when its pagination button is clicked. This is a deliberate exception to "server state → TanStack Query" (Customers and Orders do the same). The cache is cleared on logout/expired session.
- **Product details** (`GET /products/{id}`, UUID or Shopify ID — not the handle) render in the _same page_ at `/products/:id` (route `products/*` → `ProductsPage`), never in a slide-over. Opening is only via the product name, the View button or the mobile card (not the rest of the row). **Open in Shopify**: there is no Shopify column — each row's external-link icon sits in the Product cell **right after the copy icon**, both in the same 20px box with a 15px icon so they line up (`ShopifyLink` in `ProductsList.tsx`). It opens that product in the Shopify admin in a new tab — `https://admin.shopify.com/store/<store>/products/<shopify_id>` (`shopifyAdminProductUrl` in `utils/format.ts`: the store is the row's `shop.domain` minus `.myshopify.com`, accepted only if it is a plain `*.myshopify.com` address; the id must be a positive whole number; otherwise **no icon is drawn**, never a guessed link). It is a real link with `rel="noopener noreferrer"` and does not open the product in the CRM. The phone cards have no such link. **Copying a name**: in the desktop table a small copy icon (`components/ui/CopyButton.tsx`) is **always visible**, vertically centred right beside a product's name (name and icon are both 20px high); clicking it copies exactly the product name (it does not open the product) and shows a tick for a moment. Clicking a row's _image_ instead opens a right-hand quick-view panel (`ProductQuickView`, local state in `ProductsPage`) built from the already-loaded list row, with an "Open full details" button. In the Overview tab the left column shows the main image plus a single scrolling row (`components/ui/ScrollRow.tsx`, with arrows that appear only when there is more to scroll) of a thumbnail of every product image; clicking any of them (or "View Full", or an image on the Media tab) opens the lightbox. There is **no "Status & Launch" card** (removed by choice; a product's status is changed from the dropdown in the list's row); "Description" starts collapsed (`defaultOpen={false}`); "Product Specifications" starts open. **The lightbox shows each picture's `alt_text`** in a small panel at the top right beside the picture (`ProductLightboxView`, `render.controls`: a frosted-glass card with an image icon badge and no label, placed 16px from the shown picture's right edge (`AltTextCard` measures `.yarl__slide_image`; top-right of the window when there is no room beside it); "No alt text" in grey italics when it is empty; it follows the picture when paging; `LightboxSlide.altText` is unset — so no panel — for a slide that isn't a product image). The page keeps a strip of open-product **tabs** (`tabs` in `productsSlice`). Details are cached in the slice (`details`); hovering the name or View prefetches them, and the header draws from the already-loaded list row (`preview`) while the rest loads. The **Metafields tab is written for people, not for developers** (`MetafieldsPanel`, with the pure helpers in `utils/metafields.ts`, tested): a one-line explanation of what metafields are; then a table of Detail (a plain name — `unit_of_sale` → "Unit of sale", with its group and the technical `namespace.key` in small grey underneath), Applies to ("Whole product" or "Variant: …"), Kind (`number_integer` → "Whole number", `list.single_line_text_field` → "List of text (one line)"…) and Value laid out by its kind (numbers formatted, Yes/No, dates, lists as chips, small objects as label/value rows, money/weight/rating as words, colours with a swatch, links only if http(s), Shopify references as "Product 42"); structured data has a "View original value" disclosure with the pretty-printed original. The `apd` description-sections metafield is described ("2 sections: …", shown in the Description card) instead of printing its JSON. Nothing is hidden: every metafield of the product and of each variant is listed. There is **no Raw data tab** on a product (removed): the product page never asks for the large Shopify `raw_json` (`include_raw` is always sent as `false`; the slice still knows how to cache a raw copy under `"id|raw"`, unused by the page). Product description HTML is never injected as markup (the Description card rebuilds it through `SafeHtml`; elsewhere it is plain text via `htmlToText`) and links go through `safeUrl` — see also the **description sections** below, which are rebuilt by a whitelist renderer, never injected as markup. **Description sections**: the details call is `GET /products/{id}?include_raw=false&shop=` (`api.products.details`; the answer is `{ product: {…} }`; `include_raw` is always sent because the API's own default is `true`, and the large raw payload is only asked for when the Raw data tab opens). Many stores keep their description as sections ("Product Description", "Product Information"…) saved by a description app in the product metafield **`apd` / `apd`** (a JSON string: `{ sections: [{ title, content (HTML), position }], accordian_multi, … }`). `readDescriptionSections` (`utils/descriptionSections.ts`, Zod-checked; a missing, damaged or title-less value gives nothing) reads them in `position` order, and the **Overview tab shows them as an accordion inside the one "Description" card** (`DescriptionCard` in `ProductDetailPanels.tsx`: the same `EditableCard` as the cards above — icon, title, count, pencil and chevron — open to begin with, holding `DescriptionAccordion.tsx`: a bordered row per section with its title and a chevron, all closed to begin with; `accordian_multi: false` makes opening one close the others). There is **no separate card for the product's own `description_html`** any more: the sections _are_ the Description. Only a product with no sections (no/damaged `apd`) falls back to a Description card holding its own `description_html`, shown with its structure through `SafeHtml` (paragraphs, bold, lists, tables), starting collapsed, with a rich-text pencil. **The sections are editable**: the Description card's pencil turns all the sections into a form (`edit/DescriptionSectionsSection.tsx`) — a title and a rich-text editor per section, move up/down, remove (at least one stays) and **Add section** — with ✓ Save / ✕ Discard. Saving sends only the `apd` metafield through `PUT /products/{id}`'s `metafields` (`[{ namespace: 'apd', key: 'apd', type, value }]`, the type the metafield already has, else `json_string`): `buildSectionsMetafield` (`utils/descriptionSections.ts`) writes the whole JSON string — every other setting in it (`accordian_multi`, colours…) and each section's own extra keys are kept, `position` is renumbered from the new order — and sends nothing when no title/text/order changed (an untouched section's HTML is never re-written). Every section needs a title (`descriptionSections.N.title`); a product without an `apd` metafield shows its own description instead (the API has no way to create the sections' settings from scratch here). It is confirmed first like every update, and `patchMetafields` (`app/store/productPatch.ts`) puts the new value into every cached copy the moment the server confirms, so the accordion updates with no loader. Their HTML goes through `components/ui/SafeHtml.tsx`: parsed with `DOMParser` (inert), rebuilt as React elements from an allow-list (paragraphs, headings, bold/italic, lists, tables, links), scripts/styles/frames/images/forms dropped, no attributes copied except an http(s) link address (always `rel="noopener noreferrer"`) and a cell's span, empty `&nbsp;` paragraphs shrunk to small gaps. The metafield's own colours and fonts are not used; the CRM's theme is.
- **Customers** (`GET /customers`) is a sidebar page at `/customers` (entry in `navigation.ts`), built exactly like the products list (every request goes through `api.customers.list` in `endpoints.ts`; tests replay the documented query and response): `src/app/store/customersSlice.ts` (filters, per-query cache with stale-while-revalidate, previous results while loading, next-page prefetch, cleared on logout), `features/customers/hooks/useCustomers.ts` as the only consumer — **"All Customers" sends `role=all`** (the API's own default, when no role is sent, is `subscriber` only, which would silently hide administrators and make the All count wrong; `toCustomerParams` always sends a role) — and nothing is loaded at sign-in or on hovering the link — the page asks for its list once when it opens. **Figure cards** (`CustomersKpis`, the first thing on the page, above the open-customer tabs, hidden while a customer is open; the shared `KpiCards`): they make **no request of their own** — the customers list answer has no summary block, and a request per figure made the page ask for customers four times. **Customers** is the answer's `total` (everyone matching the list); **With orders**, **Without orders** and **Email subscribers** are counted among the customers on the current page (`orders_count`, `accepts_marketing`) and their captions say "Of the N on this page". For true totals of those three the backend would have to add a summary block to `GET /customers`. **Customer details** (`GET /customers/{id}`, UUID, Shopify ID or email) render in the _same page_ at `/customers/:id` (route `customers/*` → `CustomersPage`), opened only via the View button/card; the list stays mounted but hidden. **Open-customer tabs** (same as Products): a strip above the page (`CustomerTabsBar`, built on the shared `components/ui/OpenTabsBar.tsx` that `ProductTabsBar` uses too) — "All Customers" returns to the list, each opened customer is a tab (small "Customer" label + their name, email as hover text) you can switch to or close, and **Clear** closes them all; hidden until one is open. The tabs are `customersSlice.tabs` (max 10, oldest dropped; `useCustomerTabs`; cleared on logout; a deleted customer's tab is removed), a customer opened from a bare URL gets a tab too (`useCustomerDetails`) labelled once the details load, and switching to an opened customer is instant from the details cache. **Deleting a customer** (`DELETE /customers/{ref}?shop=`, `api.customers.remove` in `endpoints.ts`; the answer is read only for a `message`): permanent, in the store **and** the CRM, and Shopify refuses it for a customer with orders (the backend then says why). Each table row has a trash button next to View ("Actions" column), and the customer's own page has a Delete button in its header (the phone cards have none; open the customer). It never sends anything by itself: it opens `CustomerDeleteDialog` (`components/ui/Dialog.tsx`; **Cancel** focused) saying "This will also delete this customer in Shopify. Are you sure you want to delete this customer? It can't be undone.", with a warning line when the customer has orders. `useDeleteCustomer` wraps the `deleteCustomer` thunk; the moment the server confirms, `deleteCustomer.fulfilled` takes the customer out of every cached page (totals corrected) and the details cache, so the row is gone with no loader, then the list and the role counts are re-read quietly. Deleted from its own page, you go back to the list. A success banner shows the backend's message; a refusal (or any failure) shows the backend's message inside the dialog, which stays open, and nothing changes behind it. Writes are never retried. **Columns**: the table always shows (no checkbox column, **no Columns menu** — removed by choice) **Customer name** (name + email), **Email verified**, **Orders**, **Amount spent**, **Role**, **Joined**, **Last login** and Actions, in a fixed-layout table (`table-fixed`, `min-w-[1200px]`) whose seven columns after the name are **equal width** (`w-36`, Actions `w-28`) so the gaps are even, and whose shared cell class `TD` carries **no alignment** (a `text-left` there beats the `text-center` added next to it — each cell sets its own) where each header shares its cell's alignment: name left; Email verified, Role, Joined, Last login and Actions centred; Orders and Amount spent right-aligned; the Verified / Not verified and role pills are all one width (`w-28 justify-center`). Store, Note, Location, State and Tags are **not columns** (removed by choice; the list API doesn't return a `note` anyway). **Email verified** is the list item's `verified_email` flag (the same field the details answer carries as `verified_email`): true → Verified, false → Not verified, absent/null (CRM-only customers, or a list answer that doesn't include it) → a dash. The old **Email subscription** column (`accepts_marketing`) is gone from the table — the Marketing filter and the export's "Email subscription" column still use it. The phone cards still show the store and location line. The API also accepts `source` (`shopify` | `crm`) and `limit`, but the page deliberately has no Source filter (removed earlier by choice; `source` stays in `CustomerListParams` only) and uses `page_size`. **Filters** (the collapsible grid, same compact size and column counts as the Orders page — `SelectField compact`): **Customer role** first — one dropdown, "All Customers (9,762)", "Administrators (2)", "Subscribers (9,760)", each choice with its count; there are **no role tabs** any more, just as on Products — then Account State, Marketing, Orders, Sort by and Order, plus the Country select beside the **Filters** button and Clear All in the search row; there is deliberately **no Tag, Min spent or Max spent filter** on the page (they stay in the filters slice and in the export dialog's Advanced filters). Table and toolbar text sizes match the Orders page (`px-3 py-3` cells, 0.7rem headers, 0.85rem body). A section checks its fields _first_ — an invalid edit shows its problems and never asks (`useSectionEdit`: `commit` validates and sets `confirming`, `confirmSave` sends); the bulk editor asks first and then validates. Deleting, adding media and creating a product keep their own dialogs/forms. In tests, answer it with `confirmUpdate(user)` from `src/test/confirmUpdate.ts` (a no-op when nothing was asked). **Only fields the API has can be edited**: every edit form maps to a field of `PUT /products/{id}` (`ProductUpdateBody` / `ProductVariantInput`), and `editDraft.test.ts` ("the update body only has fields the API has") changes every editable field at once and fails if the body ever contains a key outside the API's list — add a field to the form only after the API has it. When a push fails, the red "Not sent to the store · Retry" badge now also prints the backend's reason next to it (the latest sync-history item's `error`, as plain text), so the cause is visible without hovering. The backend passes Shopify's error on as a Python-style dump, so `readableSyncError` (`utils/sync.ts`) shows just its first `message` (the full text stays in the tooltip), and `syncFailureHint` adds "Retry will not help" when the store refused for a missing permission (`ACCESS_DENIED` / access scope). Example: editing an image's alt text pushes Shopify's `fileUpdate`, which needs the app's **`write_files`** (or `write_themes`) access scope — the app's request (`media_update: [{ attachment_id, alt }]`, nothing else; tested) is correct, so that failure is fixed by granting the scope on the Shopify app the backend uses (then Retry), not in the frontend. Adding to a collection is by CRM collection ID (no list-collections endpoint yet). **Media belongs to the product; a variant just points at one of its images.** In the Variants editor each variant's "Image" dropdown lists the product's images and **preselects the one it shows now** (`variantImageId`: the image whose file equals the variant's `image_url`, ignoring the `?v=` query); only a _different_ choice is sent, as `image_attachment_id` (the API has no way to clear it). **Variants tab layout**: one row on top with the options ("Size: Small, large") on the left and the pencil (or Save / Discard) on the right (`VariantsHeader`), then a fixed-layout table (`DetailTable fixed`) with set column widths — Variant 20%, SKU 16%, Barcode 12%, Price, Compare at, Stock and Weight right-aligned, Availability centred — so the gaps are even. The Media tab labels every image "Product image" or "Variant: Small, Large" (the variants that show it). There is no "add media for a variant" call — `POST /media` has no variant field — so a picture is added to the product first and then chosen in the variant (when creating a product, a variant's picture address is added to `media` for you, see "Adding a product"). **The Variants tab edits and removes existing variants only — there is deliberately no "Add a variant"**: `ProductUpdate` has no `options` field (options and option values can't be added or renamed on an existing product), and sending a lone new variant (`variants: [{ option_values, price }]` without `id`) made the backend drop the product's other variants. (Since then the update API gained `options_add`, `variants_remove`, `metafields`/`metafields_remove` (product and per variant) and `variants[].tax_code`; `ProductUpdateBody` / `ProductVariantInput` in `endpoints.ts` have these fields, but only the product `metafields` are used by a screen — the description sections.) Bring it back only once the backend can add a variant without touching the others (and, ideally, manage options and set a new variant's stock/image — `VariantIn` has no `stock`/`image_url`, `VariantCreateIn` does). Sibling elements in a page need distinct `key`s (`details-…`, `edit-…`, `quick-view-…`): a shared key duplicates elements.
- **Write answers are enveloped** — `PUT /products/{id}`, `POST …/push` and `DELETE /products/{id}` answer `{ code, status, message, result: { product_id, sync_status, push_id, changes, message } }`, not the fields alone. `productWriteResponseSchema` in `endpoints.ts` reads `result` (and still accepts the bare fields); a schema that expects the wrong shape throws _after_ the server has already applied the change, which the UI shows as "Something went wrong" even though it saved — so check a new endpoint's real answer in the Network tab, not just the OpenAPI schema (create really answers under `product`, not `result` — the product was made and the form still reported an error). Likewise the sync history answers `{ …, items: [] }`.
- **Sync products** (`POST /sync/products?shop=`, `GET /sync/status?entity=products&limit=&shop=` — `api.sync.*` in `endpoints.ts`). The top bar (`AppBar`) shows a **Sync products** button on pages whose `NAV_ITEMS` entry has `syncs: 'products'` (Products); `SyncProductsButton` is exported through the products feature's `index.ts`. One click starts it — **no confirmation** (the button's tooltip names the stores) — and the sync runs **in the background on the server**: the button answers at once and shows "Syncing… N" (records read, from the run's status), and `useProductsSync` follows the run with TanStack Query (`useQueries` per store, polled every 3 s while a run that started after the click is unfinished; it ignores older finished runs, tolerates a 15 s clock difference, stops waiting for the run to show up after 60 s and following after 15 min). **The list refreshes while the run is still going** — each time the run's progress moves (records read/written) the current page is re-read quietly (`useRefreshProductList`, no loader), so products appear as the server saves them instead of only at the end — and when the run ends the status tab counts are refreshed too; the result ("Synced 448 products" / the run's error) stays beside the button for 15 s. Which stores: the one selected in the top-bar dropdown, or — with **All shops** — every connected, active store (the API's own default would sync only one), one `POST` per store in turn; a failure part-way keeps following the stores that did start and shows the backend's message. The trigger's answer is read leniently (only success matters), the run list accepts a bare list or `{ items }`. Writes are never retried.
- **Media** (Media tab of the details page). Adding and deleting files use their own endpoints, both in `endpoints.ts`: `POST /products/{id}/media?shop=` with `{ items: [{ url, alt?, media_type }] }` (1–20 per call, public https URLs; Shopify downloads each file to its CDN, so the answer is only "Media queued for Shopify" and the attachments appear a little later) and `DELETE /products/{id}/media/{attachment_id}?shop=` ("Media removal queued"); both answer the enveloped `ProductWriteResult`. They are immediate actions, not part of the in-place edit's Save: the tab's header row (like Collections) has the pencil — which now edits only **alt text and order** (`media_update` / `media_order` through the normal `PUT`, so nothing in it can lose a file) — and an **Add media** button opening `AddMediaDialog` (a form of rows: address, alt, type; checked first with `validateNewMedia` — https only, the API's length limits, at most 20 — and sent as `buildMediaItems`), and every tile has a **Delete** button opening `DeleteMediaDialog` (Cancel focused; nothing is sent until Delete). `useProductMedia` wraps the `addProductMedia` / `removeProductMedia` thunks: a deleted image leaves every cached copy at once (`removeProductMedia.fulfilled` → `patchCachedProduct`, so the tab, gallery and counts update with no loader), **and stays gone**: the delete is only _queued_ in the store ("Media removal queued"), so the quiet re-read that follows can still list the image and would put it back until a manual refresh. `removeProductMedia.fulfilled` therefore also records it in `productsSlice.removedMedia` (id + file URL, by product), and `fetchProductDetails.fulfilled` hides every recorded image the backend still lists (`hideRemovedImages` in `productPatch.ts`; matched by id _or_ by file ignoring the `?v=` query, since ids can change) and forgets it as soon as the backend stops listing it — or after 10 minutes, so an image that really is still there is never lost for good — while added files show as **Processing…** tiles (`usePendingMedia`: the submitted URLs, checked against the product every 4 s, each arriving image replaces one tile) until the store has finished. The waiting files live in `productsSlice.pendingMedia` (by product id, cleared on logout), **not** in the tab, so they survive leaving the Media tab or the product, and the header counts them ("1 processing") instead of saying "No images". **Looking for them**: `usePendingMedia` checks the product every **2 s for the first 30 s**, every 4 s until 60 s, then every 16 s (a file is usually ready within seconds, and a long wait makes people add it again). **No double uploads**: `useProductMedia.add` ignores a second call while one is in flight (a ref, checked synchronously — `isAdding` only turns true on the next render), and the same address twice in one request is refused (`validateNewMedia`: "This address is already in the list above") and dropped by `buildMediaItems`. They are never dropped just because the store is slow: after 60 s the tiles read "Still waiting for the store", a notice explains that the store only accepts a direct public image link (and that Sync products brings the image in too) with a **Dismiss** button, and the product is re-read every 16 s instead of every 4 s (until 15 min, after which the tiles simply stay until dismissed). **A page refresh keeps all of this**: the waiting files (`pendingMedia`), the just-deleted images (`removedMedia`) and the created-product previews (`previewImages`) are saved to this tab's `sessionStorage` (`app/store/productMediaStorage.ts`, wired in `store.ts`: restored at startup only for a signed-in user, written on every change, validated with Zod — https addresses only — nothing older than a day, and removed when the session ends). Without it a refresh while the store was still downloading showed "No images" even though the files were on their way. The CRM only learns an image once the backend has the store's CDN copy, so until then it cannot show it; when the images do arrive, the products list is re-read too (`usePendingMedia`), because its row was read before the store had them and would otherwise keep showing no image. Both then refresh the product, list and sync status quietly (`useRefreshAfterSave`); failures show the backend's message inside the dialog, which stays open. The two calls follow the API exactly (tests replay the documented three-image example and the documented delete): `POST /products/{product_id}/media?shop=` with `{ items: [{ url, alt?, media_type }] }` (≤ 20 per call) and `DELETE /products/{product_id}/media/{attachment_id}?shop=` with no body, where `shop` is the product's store key. **Address check**: Shopify does not accept SVG, and placeholder services such as placehold.co answer with an SVG unless the address ends in `.png`/`.jpg` — so `svgImageWarning` (`utils/format.ts`) shows a warning under the preview for an `.svg` address or a placehold.co address without a raster extension (a hint only, it never blocks). The API also has a direct-upload route (`POST …/media/upload-target`, then the returned `resource_url` goes in `url`); the app does not use it. Writes are never retried, with one deliberate exception: **image ids can change** (the store re-syncs a product after a change), and the backend then answers a delete with 422 "Image … is not an image of this product". So `DeleteMediaDialog` re-reads the product as it opens, `useProductMedia.remove` deletes by the freshest id it knows for that file (matched by URL), and if the backend still doesn't know the image it re-reads the product and retries **once** with the file's current id (only after a rejection — nothing was deleted — and only if the id differs); an image that is gone after the re-read gets a plain message. Any other failure is not retried.
- **Status dropdown in the list** — a row's status is a `ProductStatusSelect` (`components/ProductStatusSelect.tsx`): the status pill is a button that opens a **colour-coded listbox** — each option is the same pill as the table shows (Active green, Draft grey, Archived red, via `components/ui/badgeTones.ts`, with a ✓ on the current one) — offering Active / Draft / Archived (what the API can set; Unlisted is shown disabled). - **Adding a product** (`POST /products`, `api.products.create` in `endpoints.ts` — body `ProductCreateBody`: `shop`, `title` and at least one priced variant are required; the answer is a `ProductCreateResult` (`product_id`, `shopify_id`, `handle`, `title`, `status`, counts, `message`), the real answer is `{ code: 201, status, message, product: { product_id, … } }` — the fields sit under **`product`** (the OpenAPI spec doesn't say so); `productCreateResponseSchema` also accepts `result` and the bare fields). - Error messages shown to users come from the backend: `lib/api/client.ts` turns a failed response into an `ApiError` whose `message` is the first field error (422) or the body's `message`, with a friendly fallback for network failures/timeouts.
- The backend rejects browser CORS from localhost, so dev/preview proxy `/api` to `https://polymeruk-api.vercel.app` (see `vite.config.ts`). On Vercel, `vercel.json` does the same job: it rewrites `/api/*` to the backend (without it every API call 404s), serves `index.html` for deep links like `/products/<id>`, and marks `/api/*` responses `no-store`. `VITE_API_BASE_URL=/api` (the default) sends requests through that rewrite, so the browser's Network tab shows your own domain's `/api/...` — that is the proxy, not a bug. Setting it to the full backend URL (`https://polymeruk-api.vercel.app/api`) makes the browser call the backend directly instead; the CSP `connect-src` in `vercel.json` already allows that host. Direct mode only works on origins in the backend's CORS list (currently just `https://polymer-frontend.vercel.app`: previews, other domains and localhost get blocked) and adds a CORS preflight per distinct authenticated URL, so the proxy is the default. Keep `/api` in `.env.local` for local development.
- Not done yet: showing the real signed-in user (`currentUser.ts` is still a placeholder) and `GET /auth/me`.

## Security

The browser is untrusted: real authorization lives in the backend. The frontend's job is to not leak the token, not run injected code, and fail safely. Guarded by tests in `src/config/` and `src/lib/api/client.test.ts` — keep them passing.

- **Headers** (`vercel.json`, production only): a strict Content-Security-Policy (`script-src` is `'self'` plus Google's sign-in script only — **never add `'unsafe-inline'`/`'unsafe-eval'` to scripts**), `X-Frame-Options`/`frame-ancestors` (no framing), `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS, and `no-store` on `/api/*`. Inline _styles_ are allowed (`style-src-elem`/`style-src-attr`) only because Google's button injects them; without that the button renders unstyled. `securityHeaders.test.ts` locks this in. After changing the policy, load the built site with the real headers in a browser and check the console for violations (the dev server sends no CSP).
- **No inline scripts**: the pre-paint theme script is the static file `public/theme-init.js` (a deliberate exception to "no new `.js` files" — it must be a same-origin file so the CSP can forbid inline scripts). Keep it in sync with `uiSlice.ts`.
- **No secrets in the bundle**: every `VITE_` variable is public. Never name one `*SECRET*`/`*TOKEN*`/`*KEY*`/`*PASSWORD*`; `secrets.test.ts` fails on that, on hard-coded credentials, on `import.meta.env` outside `config/env.ts`, and on `console.*` in production code. Source maps are off (`build.sourcemap: false`).
- **Safe rendering**: no `dangerouslySetInnerHTML`/`innerHTML`/`eval` (tested). API text is rendered as text; HTML descriptions go through `htmlToText`; API-supplied URLs go through `safeUrl` (http/https only) before use as `href` or `<img src>`; `target="_blank"` always has `rel="noopener noreferrer"`; third-party images send no referrer.
- **Errors**: `ApiError` carries only `status`/`data`/`code` (never the Axios request config, which holds the `Authorization` header). Users see the backend message or a friendly fallback (403/404/429/5xx/network). Render crashes show `ErrorFallback` (via `AppErrorBoundary` and the router's `RouteErrorPage`) with no technical detail in production.
- **Requests**: GETs retry twice (400 ms, 1.2 s) on network drops and 502/503/504 only; POST/PUT/PATCH/DELETE are **never** retried (a repeat could duplicate a write); timeouts, 4xx and 401 are never retried.
- **Session** (`hooks/useSessionGuard.ts`, used by `DashboardLayout`): signs out when the session passes its `expiresAt` (30 days after signing in — see "Staying signed in"; there is deliberately no inactivity sign-out) and when another tab logs out; the login page says why (`signedOutReason`). A stored session is shape-validated before use. The token itself still lives in `localStorage` (readable by any script that runs on the page — the CSP is the mitigation); an `HttpOnly` cookie session would need a backend change.

## Rules

1. **Import features only through their `index.ts`.** Never `import { X } from '../../features/other/components/X.tsx'`. If it's not exported from `index.ts`, it's private to that feature.
2. **Features don't reach into each other's internals**, and avoid feature-to-feature dependencies where practical — prefer lifting shared code to `lib/`, `hooks/`, or `components/ui/`.
3. **No raw Axios/`fetch` in components or pages.** Go through a feature's `api/` module, which goes through `apiClient`.
4. **Don't add a dependency without checking this file and `package.json` first** for something that already solves the problem. The state/data/HTTP/validation/styling stack (Redux Toolkit, TanStack Query, Axios, Zod, Tailwind) is deliberately chosen — don't add a second competing library for any of those roles (no RTK Query _and_ a hand-rolled fetch hook; no a second HTTP client; no a second schema/validation library; no CSS-in-JS or CSS Modules alongside Tailwind).
5. **Server state goes through TanStack Query; client state goes through Redux.** Don't put fetched data in a Redux slice, and don't reach for `useState`/prop-drilling for something two+ unrelated components need — add a slice instead. Local component state is still the default for anything that's neither.
6. **Don't create empty placeholder directories** "for later." Add a subdirectory when the first file that belongs in it exists.
7. **Keep `App.tsx`, `main.tsx`, and `AppRouter.tsx` thin.** They wire things together; they don't contain business logic, data fetching, or complex JSX.
8. **Secrets never get committed.** Anything sensitive goes in `.env.local` (git-ignored), not `.env.example`, and never hardcoded.
9. **Type safety is not optional.** `strict` mode is on; don't add `any` or `@ts-expect-error`/`@ts-ignore` to route around a type error — fix the type. A feature's types come from its Zod schema (`z.infer`), not a hand-written `interface` duplicating it.

## What a page requests when it opens

**A page makes its requests when it is opened (a click) — only the GETs it shows, and nothing before.** No list is loaded at sign-in, hovering a sidebar link or a pagination button requests nothing, no next page is fetched on its own, the store list (`GET /shops`) is only requested on a page that shows the store dropdown (`AppBar`'s `ShopScope`), and filter-specific requests — the counts inside a filter dropdown, the Activity action choices — wait until the Filters grid is opened or the dropdown is reached for. Applying a filter asks for that filtered list (and, with the grid open, its counts). Figures above a list are read from the list's own answer, never from extra requests. The one remaining hover request is a record's **details** (the name/View button of a row), which is deliberate. `app/layouts/initialLoad.test.tsx` renders the whole shell against a fake backend that records every request and fails if a page's start-up grows.

## Mock data

A feature without a backend yet follows this pattern (Orders and Products used to; both are real now):

- `schemas/*.ts` defines a Zod schema for the shape (e.g. `orderSchema`) and derives the TS type from it (`export type Order = z.infer<typeof orderSchema>`) — the schema is the source of truth, the type is generated from it, not maintained separately.
- `api/mock*.ts` exports a `get*()` function returning a `Promise` that resolves with an array after a simulated delay (real loading states, no real network call), validated against the schema (`orderSchema.array().parse(...)`).
- `hooks/use*.ts` wraps that in TanStack Query's `useQuery` and normalizes its status to `{ data, status: 'loading' | 'success' | 'error', error }` (React Query's own status is `'pending' | 'success' | 'error'` — mapped so pages don't need to know that).
- The page renders all three states via `components/ui/Table`'s `TableState` row, not just the happy path.

**To connect a real backend**, change only what's inside `get*()` — call `apiClient` from `src/lib/api/client.ts` instead of returning mock data, `.parse()` that response against the same schema, and delete the `TODO` comment above it. The hook and page don't need to change. Follow the same `schemas/` + `api/` + `hooks/` shape for any new feature that fetches data — don't invent a different pattern per feature.

## Testing conventions

- Co-locate: `Foo.tsx` → `Foo.test.tsx`, in the same directory.
- Use React Testing Library queries by role/label/text (`getByRole`, `getByLabelText`) — avoid querying by class name or test-only attributes unless nothing else identifies the element.
- Anything that renders a component touching Redux, TanStack Query, or routing needs `src/test/renderWithProviders.tsx` instead of RTL's plain `render` — it wraps the tree in a **fresh** Redux store and QueryClient per call (not the app's singletons), so tests don't need to manually reset shared state between runs, plus a `MemoryRouter`.
- `vitest.config`'s `test` block lives in `vite.config.ts`; `src/test/setup.ts` registers jest-dom matchers. `globals: true` is set, so `describe`/`it`/`expect` are available without importing them (this repo's tests import them explicitly for clarity — either style works).

## Common mistakes to avoid

- Putting a feature-specific component in `components/ui/` because it "might be reused later." Wait until it actually is.
- Importing `features/x/pages/SomePage.tsx` directly from another feature or from `app/router` instead of importing it from `features/x/index.ts`.
- Calling `axios`/`fetch` directly instead of extending `lib/api/client.ts`.
- Fetching data with `useEffect` + `useState` instead of TanStack Query, or putting server data in a Redux slice instead of a query cache.
- Reaching for a second global-state approach (Context-for-everything, a new store library) instead of adding a Redux slice.
- Hand-writing a type that duplicates a Zod schema's shape instead of deriving it with `z.infer`.
- Reading `import.meta.env.VITE_*` outside `src/config/env.ts`.
- Adding a second formatter/linter (e.g. ESLint) alongside the existing Prettier/Oxlint setup.
- Adding an icon library or a new global font import — the icon set is hand-rolled in `components/ui/icons.tsx`, and `'Neue Haas Unica Pro'` (commercially licensed, not bundled) is the intended typeface; self-host a licensed webfont file rather than pulling one from a public CDN.
- Adding a `.js`/`.jsx` file, or importing with a `.js` extension that actually points at a `.ts`/`.tsx` file.
- Creating a new `ComponentName.css` file, or writing a `dark:` variant class — see "Styling" above for why neither is needed.
